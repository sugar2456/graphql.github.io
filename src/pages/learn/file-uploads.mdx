# GraphQLでのファイルアップロードの処理

GraphQLは、ファイルアップロードを念頭に置いて設計されていません。技術的には実装可能ですが、トランスポート層を拡張する必要があり、セキュリティと信頼性の両方でいくつかのリスクが導入されます。

このガイドでは、GraphQL経由でのファイルアップロードが問題となる理由を説明し、より安全な代替案を提示します。

## アップロードが困難な理由

[GraphQL仕様](https://spec.graphql.org/draft/)は、トランスポートに依存せず、シリアル化にも依存しません（ただし、HTTPとJSONはコミュニティで最も一般的な組み合わせです）。GraphQLは、クライアントからの比較的小さなリクエストで動作するように設計されており、バイナリデータの処理を念頭に置いて設計されていません。

対照的に、ファイルアップロードは通常、画像やPDFなどのバイナリデータを処理します—JSONを含む多くのエンコーディングが直接処理できないものです。1つのオプションは、エンコーディング内でエンコードすることです（例：JSON内でbase64エンコードされた文字列を使用する）が、これは非効率的であり、ストリーミング処理を簡単にサポートしないため、大きなバイナリファイルには適していません。代わりに、`multipart/form-data`はバイナリデータを転送するための一般的な選択肢ですが、それ自体の複雑さのセットがないわけではありません。

GraphQL経由でのアップロードのサポートには、通常、コミュニティの慣行を採用することが含まれます。その中で最も一般的なのは、[GraphQL multipart request specification](https://github.com/jaydenseric/graphql-multipart-request-spec)です。この仕様は多くの言語とフレームワークで正常に実装されていますが、実装するユーザーは、セキュリティや信頼性の問題を導入しないように細心の注意を払う必要があります。

## 認識すべきリスク

### 繰り返し変数によるメモリ枯渇

GraphQL操作では、同じ変数を複数回参照できます。ファイルアップロード変数が再利用される場合、基盤となるストリームが複数回読み取られるか、早期に枯渇する可能性があります。これは、不正な動作やメモリ枯渇を引き起こす可能性があります。

安全な慣行は、信頼できるドキュメントまたは検証ルールを使用して、各アップロード変数が正確に1回だけ参照されることを保証することです。

### 失敗した操作でのストリームリーク

GraphQLは段階的に実行されます：検証、その後実行。検証が失敗した場合、または認可チェックが実行を早期に終了した場合、アップロードされたファイルストリームが消費されない可能性があります。サーバーがこれらのストリームをバッファリングまたは保持する場合、メモリリークを引き起こす可能性があります。

これを回避するには、リゾルバで消費されたかどうかに関係なく、リクエストが終了したときにすべてのストリームが終了されることを確認します。考慮すべき代替案は、受信ファイルを一時ストレージにすぐに書き込み、リゾルバに参照（ファイル名など）を渡すことです。成功または失敗に関係なく、リクエスト完了後にこのストレージがクリーンアップされることを確認してください。

### クロスサイトリクエストフォージェリ（CSRF）

`multipart/form-data`は、CORS仕様で「シンプル」なリクエストとして分類され、プリフライトチェックをトリガーしません。明示的なCSRF保護がない場合、GraphQLサーバーは悪意のあるオリジンからのアップロードを気づかずに受け入れる可能性があります。

### 過大または過剰なペイロード

攻撃者は、非常に大きなアップロードを送信したり、未使用の変数名の下に余分なファイルを含めたりする可能性があります。これらを受け入れ、バッファリングするサーバーは圧倒される可能性があります。

リクエストサイズの上限を強制し、multipartペイロードのmapフィールドで明示的に参照されていないファイルを拒否します。

### 信頼できないファイルメタデータ

ファイル名、MIMEタイプ、コンテンツなどの情報は、決して信頼すべきではありません。リスクを軽減するには：

- パストラバーサルまたはインジェクションの問題を防ぐためにファイル名をサニタイズします。
- 宣言されたMIMEタイプとは独立してファイルタイプを検出し、不一致を拒否します。
- ファイルコンテンツを検証します。zip爆弾や悪意を持って作成されたPDFなどの形式固有のエクスプロイトに注意してください。

## 推奨事項：署名付きURLを使用する

最も安全でスケーラブルなアプローチは、GraphQL経由でのファイルアップロードを完全に回避することです。代わりに：

1. GraphQLミューテーションを使用して、ストレージプロバイダー（例：Amazon S3）から署名付きアップロードURLをリクエストします。
2. そのURLを使用して、クライアントから直接ファイルをアップロードします。
3. アップロードされたファイルをアプリケーションのデータに関連付けるために、2番目のミューテーションを送信します（または、Amazon Lambdaなどの自動的にトリガーされるプロセスを使用して同じことを行います）。

攻撃者がステップ1と2のみを完了した場合にストレージが枯渇しないように、これらのファイルアップロードが短期間のみ保持されることを確認する必要があります。ファイルアップロードを処理する際（ステップ3）、ファイルは適切に永続ストレージに移動する必要があります。

これは責任を明確に分離し、サーバーをバイナリデータの処理から保護し、モダンなWebアーキテクチャのベストプラクティスに沿っています。

## それでもアップロードをサポートすることを選択する場合

アプリケーションがGraphQL経由でのファイルアップロードを真に必要とする場合、注意して進めてください。最低限、以下を行う必要があります：

- [GraphQL multipart request spec](https://github.com/jaydenseric/graphql-multipart-request-spec)の適切に維持されている実装を使用します。
- アップロード変数が1回だけ参照されるルールを強制します。
- アップロードをディスクまたはクラウドストレージにストリーミングします—メモリにバッファリングしないでください。
- 消費されたかどうかに関係なく、リクエストが終了したときにストリームが常に終了されることを確認します。
- 厳格なリクエストサイズ制限を適用し、すべてのフィールドを検証します。
- ファイル名、タイプ、コンテンツを信頼できないデータとして扱います。
