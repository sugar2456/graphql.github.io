# サブスクリプション

import { Callout } from "nextra/components"

<p className="learn-subtitle">GraphQLサーバーからリアルタイムの更新を取得する方法を学ぶ</p>

ステートレスなクエリとミューテーション操作を使用してデータを読み書きすることに加えて、GraphQL仕様は、長期間にわたるリクエストを介してリアルタイムの更新を受信する方法も説明しています。このページでは、クライアントがサブスクリプション操作を使用してGraphQLサーバー上のイベントの詳細をサブスクライブする方法について説明します。

<Callout type="info">
クエリに適用されるGraphQL操作の機能の多くは、サブスクリプションにも適用されるため、先に進む前に[クエリ](/learn/queries/)ページを確認してください。
</Callout>

## 更新のサブスクライブ

サブスクリプションフィールドは、`Query`フィールドと`Mutation`フィールドとまったく同じように定義されますが、代わりに`subscription`ルート操作型を使用します：

```graphql
type Subscription {
  reviewCreated: Review
}
```

同様に、サブスクリプションは、操作型として`subscription`キーワードを使用して開始されます：

```graphql
subscription NewReviewCreated {
  reviewCreated {
    rating
    commentary
  }
}
```

GraphQLサブスクリプションは、通常、別のpub/subシステムによってサポートされているため、更新されたデータに関するメッセージをランタイム中に必要に応じて公開し、API内のサブスクリプションフィールドのリゾルバ関数によって消費できます。

前の例では、クライアントが`createReview`ミューテーションで新しいレビューを送信したときに、pub/subシステムに`REVIEW_CREATED`メッセージを公開し、その後、`reviewCreated`サブスクリプションフィールドのリゾルバ関数でこのイベントをリッスンして、サーバーがこのデータをサブスクライブしたクライアントに送信できるようにすることを想像できます。

<Callout type="info">
サブスクリプションは、一部のGraphQL実装が提供する可能性のある緩く定義された機能である_ライブクエリ_の概念とは異なることに注意してください。[ライブクエリの正式な仕様に関する進行中の議論について詳しく読む](https://github.com/graphql/graphql-spec/issues/386)
</Callout>

クエリとミューテーション操作と同様に、GraphQLは使用するトランスポートプロトコルを指定していないため、サーバーが決定します。実際には、WebSocketまたはサーバー送信イベントで実装されることがよくあります。サブスクリプション操作を送信したいクライアントは、選択されたプロトコルもサポートする必要があります。[WebSocket](https://github.com/enisdenjo/graphql-ws/blob/master/PROTOCOL.md)と[サーバー送信イベント](https://github.com/enisdenjo/graphql-sse/blob/master/PROTOCOL.md)でGraphQLサブスクリプションを実装するためのコミュニティが維持する仕様があります。

サブスクリプション操作で重要な区別は、ドキュメントに異なるルートフィールドを持つ複数の異なるサブスクリプション操作を含めることができるが、各操作は正確に1つのルートフィールドを持たなければならないということです。

例えば、この操作は無効です：

```graphql
subscription {
  reviewCreated {
    rating
    commentary
  }
  humanFriendsUpdated {
    name
    friends {
      name
    }
  }
}
```

しかし、このドキュメントは有効です：

```graphql
subscription NewReviewCreated {
  reviewCreated {
    rating
    commentary
  }
}
subscription FriendListUpdated($id: ID!) {
  humanFriendsUpdated(id: $id) {
    name
    friends {
      name
    }
  }
}
```

クエリとミューテーション操作と同様に、上記のドキュメントには複数の操作が含まれているため、各操作に名前を付ける必要があり、実行する操作の名前をリクエストで指定する必要があります。

## スケールでのサブスクリプションの使用

サブスクリプション操作はGraphQLの強力な機能ですが、クエリやミューテーションよりも実装が複雑です。なぜなら、サブスクリプションのライフタイムにわたってGraphQLドキュメント、変数、その他のコンテキストを維持する必要があるためです。これらの要件は、GraphQLサーバーを水平方向にスケーリングする際に困難になる可能性があります。なぜなら、サブスクライブした各クライアントは、サーバーの特定のインスタンスにバインドされる必要があるためです。

同様に、クライアントライブラリは、通常、これらの種類の操作を処理するために、より高度な機能を必要とします。接続が中断された場合に操作を再サブスクライブするロジックや、初期クエリと更新されたサブスクリプションデータの間の潜在的な競合状態を処理するメカニズムなどです。

実際には、サブスクリプションをサポートするGraphQL APIは、クエリとミューテーションフィールドのみを公開するAPIよりも複雑なアーキテクチャを必要とします。このアーキテクチャの設計方法は、特定のGraphQL実装、サブスクリプションをサポートするpub/subシステム、選択されたトランスポートプロトコル、およびリアルタイムデータの可用性、スケーラビリティ、セキュリティに関連するその他の要件によって異なります。

サブスクリプション操作は、頻繁に増分的に変更されるデータ、および期待されるユーザーエクスペリエンスを提供するために、可能な限りリアルタイムに近いこれらの増分的更新を受信する必要があるクライアントに適しています。更新頻度が低いデータの場合、定期的なポーリング、モバイルプッシュ通知、またはユーザーインタラクションに基づくクエリの再取得が、クライアントUIを最新の状態に保つためのより良いソリューションである可能性があります。

## 次のステップ

サブスクリプションについて学んだことをまとめると：

- GraphQLサブスクリプション操作は、長期間にわたるリクエストを介して増分的なデータ更新に使用できます
- サブスクリプション操作は、通常、ステートフルなトランスポートプロトコルによってサポートされているため、クエリやミューテーションよりも実装とサポートに多くの労力が必要になります
- クライアントにストリーミングするために頻繁で増分的な更新を必要とするデータ取得ユースケースは、サブスクリプションに最適です

GraphQLの3つの操作タイプすべてをカバーしたので、クライアントリクエストがGraphQLサーバーによって[検証](/learn/validation/)される方法について説明します。
