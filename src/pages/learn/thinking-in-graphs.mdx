# グラフとして考える

## グラフはすべての階層に存在する[^1]

> GraphQLでは、ビジネスドメインをグラフとしてモデル化します

グラフは、多くの現実世界の現象をモデル化するための強力なツールです。なぜなら、それらは自然なメンタルモデルと基礎となるプロセスの口頭での説明に似ているためです。GraphQLでは、スキーマを定義することでビジネスドメインをグラフとしてモデル化します。スキーマ内で、異なる種類のノードとそれらがどのように接続/関連しているかを定義します。クライアント側では、これはオブジェクト指向プログラミングに似たパターンを作成します：他の型を参照する型です。サーバー側では、GraphQLはインターフェースのみを定義するため、任意のバックエンド（新規またはレガシー！）で使用する自由があります。

## 共有言語

> 物事に名前を付けることは、直感的なAPIを構築するための困難だが重要な部分です

GraphQLスキーマを、チームとユーザーのための表現力豊かな共有言語として考えてください。良いスキーマを構築するには、ビジネスを説明するために使用する日常的な言語を調べます。例えば、プレーンな英語でメールアプリを説明してみましょう：

- ユーザーは複数のメールアカウントを持つことができます
- 各メールアカウントには、アドレス、受信トレイ、下書き、削除済みアイテム、送信済みアイテムがあります
- 各メールには、送信者、受信日、件名、本文があります
- ユーザーは受信者アドレスなしでメールを送信できません

物事に名前を付けることは、直感的なAPIを構築するための困難だが重要な部分です。そのため、問題ドメインとユーザーにとって意味のあるものを慎重に考える時間を取ってください。チームは、これらのビジネスドメインルールの共有理解と合意を開発する必要があります。なぜなら、GraphQLスキーマのノードと関係に直感的で永続的な名前を選択する必要があるためです。実行したいクエリのいくつかを想像してみてください：

すべてのアカウントの受信トレイ内の未読メールの数を取得する

```graphql
{
  accounts {
    inbox {
      unreadEmailCount
    }
  }
}
```

メインアカウントの最初の20件の下書きの「プレビュー情報」を取得する

```graphql
{
  mainAccount {
    drafts(first: 20) {
      ...previewInfo
    }
  }
}

fragment previewInfo on Email {
  subject
  bodyPreviewSentence
}
```

## ビジネスロジック層

> ビジネスロジック層は、ビジネスドメインルールを強制するための単一の情報源として機能する必要があります

実際のビジネスロジックはどこで定義すべきでしょうか？検証と認可チェックはどこで実行すべきでしょうか？答え：専用のビジネスロジック層内です。ビジネスロジック層は、ビジネスドメインルールを強制するための単一の情報源として機能する必要があります。

### レガシーデータの操作

> レガシーデータベーススキーマを反映するのではなく、クライアントがデータを使用する方法を記述するGraphQLスキーマを構築することを優先してください。

場合によっては、クライアントがデータを消費する方法を完全に反映していないレガシーデータソースで作業することになります。このような場合、レガシーデータベーススキーマを反映するのではなく、クライアントがデータを使用する方法を記述するGraphQLスキーマを構築することを優先してください。

GraphQLスキーマを「何を」ではなく「どのように」を表現するように構築してください。そうすれば、古いクライアントとのインターフェースを壊すことなく、実装の詳細を改善できます。

## 一度に一歩ずつ

> より頻繁に検証とフィードバックを得る

一度にビジネスドメイン全体をモデル化しようとしないでください。むしろ、一度に1つのシナリオに必要なスキーマの部分のみを構築してください。スキーマを徐々に拡張することで、より頻繁に検証とフィードバックを得て、正しいソリューションを構築する方向に導くことができます。

[^1]: ["Turtles all the way down"](https://en.wikipedia.org/wiki/Turtles_all_the_way_down)は、無限後退の問題の表現です。
