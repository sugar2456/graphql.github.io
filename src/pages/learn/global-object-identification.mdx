# グローバルオブジェクト識別

> 一貫したオブジェクトアクセスにより、シンプルなキャッシングとオブジェクトルックアップが可能になります

GraphQLクライアントがキャッシングとデータの再取得をエレガントに処理するためのオプションを提供するために、GraphQLサーバーは標準化された方法でオブジェクト識別子を公開する必要があります。

これを機能させるために、クライアントは標準的なメカニズムを介してIDでオブジェクトをリクエストする必要があります。その後、レスポンスで、スキーマはこれらのIDを提供する標準的な方法を提供する必要があります。

ID以外にオブジェクトについてほとんど知られていないため、これらのオブジェクトを「ノード」と呼びます。ノードのクエリの例を次に示します：

```graphql
{
  node(id: "4") {
    id
    ... on User {
      name
    }
  }
}
```

- GraphQLスキーマは、ルートクエリオブジェクトの`node`フィールドを介して任意のオブジェクトを取得できるようにフォーマットされています。これは、「Node」[インターフェース](/learn/schema/#interfaces)に準拠するオブジェクトを返します。
- `id`フィールドは、レスポンスから安全に抽出でき、キャッシングと再取得を介して再利用のために保存できます。
- クライアントは、インターフェースフラグメントを使用して、ノードインターフェースに準拠する型に固有の追加情報を抽出できます。この場合、「User」です。

Nodeインターフェースは次のようになります：

```graphql
# グローバルに一意のIDを持つオブジェクト
interface Node {
  # オブジェクトのID。
  id: ID!
}
```

Userは次のように準拠します：

```graphql
type User implements Node {
  id: ID!
  # フルネーム
  name: String!
}
```

## 仕様

以下はすべて、サーバー実装間で一貫性を確保するために準拠する必要があるオブジェクト識別に関する仕様を、より正式な要件で説明しています。これらの仕様は、サーバーが[Relay][relay] APIクライアントに準拠する方法に基づいていますが、任意のクライアントにとって有用です。

## 予約された型

この仕様に準拠するGraphQLサーバーは、一貫したオブジェクト識別モデルをサポートするために、特定の型と型名を予約する必要があります。特に、この仕様は次の型のガイドラインを作成します：

- `Node`という名前のインターフェース。
- ルートクエリ型の`node`フィールド。

## Nodeインターフェース

サーバーは、`Node`という名前のインターフェースを提供する必要があります。そのインターフェースには、非nullの`ID`を返す`id`という名前のフィールドが正確に1つ含まれている必要があります。

この`id`は、このオブジェクトのグローバルに一意の識別子である必要があり、この`id`だけが与えられると、サーバーはオブジェクトを再取得できる必要があります。

### イントロスペクション

上記のインターフェースを正しく実装するサーバーは、次のイントロスペクションクエリを受け入れ、提供されたレスポンスを返します：

```graphql
{
  __type(name: "Node") {
    name
    kind
    fields {
      name
      type {
        kind
        ofType {
          name
          kind
        }
      }
    }
  }
}
```

yields

```json
{
  "__type": {
    "name": "Node",
    "kind": "INTERFACE",
    "fields": [
      {
        "name": "id",
        "type": {
          "kind": "NON_NULL",
          "ofType": {
            "name": "ID",
            "kind": "SCALAR"
          }
        }
      }
    ]
  }
}
```

## Nodeルートフィールド

サーバーは、`Node`インターフェースを返す`node`という名前のルートフィールドを提供する必要があります。このルートフィールドは、`id`という名前の非nullIDである正確に1つの引数を受け取る必要があります。

クエリが`Node`を実装するオブジェクトを返す場合、サーバーが`Node`の`id`フィールドで返す値が`node`ルートフィールドの`id`パラメータとして渡されると、このルートフィールドは同じオブジェクトを再取得する必要があります。

サーバーは、このデータを取得するために最善の努力を払う必要がありますが、常に可能であるとは限りません。例えば、サーバーは有効な`id`を持つ`User`を返す可能性がありますが、`node`ルートフィールドでそのユーザーを再取得するリクエストが行われると、ユーザーのデータベースが利用できないか、ユーザーがアカウントを削除した可能性があります。この場合、このフィールドをクエリした結果は`null`である必要があります。

### イントロスペクション

上記の要件を正しく実装するサーバーは、次のイントロスペクションクエリを受け入れ、提供されたレスポンスを含むレスポンスを返します。

```graphql
{
  __schema {
    queryType {
      fields {
        name
        type {
          name
          kind
        }
        args {
          name
          type {
            kind
            ofType {
              name
              kind
            }
          }
        }
      }
    }
  }
}
```

yields

```jsonc
{
  "__schema": {
    "queryType": {
      "fields": [
        // この配列には他のエントリが含まれる場合があります
        {
          "name": "node",
          "type": {
            "name": "Node",
            "kind": "INTERFACE"
          },
          "args": [
            {
              "name": "id",
              "type": {
                "kind": "NON_NULL",
                "ofType": {
                  "name": "ID",
                  "kind": "SCALAR"
                }
              }
            }
          ]
        }
      ]
    }
  }
}
```

## フィールドの安定性

2つのオブジェクトがクエリに表示され、両方とも同じIDで`Node`を実装している場合、2つのオブジェクトは等しくなければなりません。

この定義の目的のために、オブジェクトの等価性は次のように定義されます：

- フィールドが両方のオブジェクトでクエリされる場合、最初のオブジェクトでそのフィールドをクエリした結果は、2番目のオブジェクトでそのフィールドをクエリした結果と等しくなければなりません。
  - フィールドがスカラーを返す場合、等価性はそのスカラーに適切に定義されます。
  - フィールドが列挙型を返す場合、等価性は両方のフィールドが同じ列挙値を返すこととして定義されます。
  - フィールドがオブジェクトを返す場合、等価性は上記のように再帰的に定義されます。

例えば：

```graphql
{
  fourNode: node(id: "4") {
    id
    ... on User {
      name
      userWithIdOneGreater {
        id
        name
      }
    }
  }
  fiveNode: node(id: "5") {
    id
    ... on User {
      name
      userWithIdOneLess {
        id
        name
      }
    }
  }
}
```

might return:

```json
{
  "fourNode": {
    "id": "4",
    "name": "Mark Zuckerberg",
    "userWithIdOneGreater": {
      "id": "5",
      "name": "Chris Hughes"
    }
  },
  "fiveNode": {
    "id": "5",
    "name": "Chris Hughes",
    "userWithIdOneLess": {
      "id": "4",
      "name": "Mark Zuckerberg"
    }
  }
}
```

`fourNode.id`と`fiveNode.userWithIdOneLess.id`が同じであるため、上記の条件により、`fourNode.name`は`fiveNode.userWithIdOneLess.name`と同じである必要があり、実際にそうなっています。

## 複数形の識別ルートフィールド

ユーザーのユーザー名を受け取り、対応するユーザーを返す`username`という名前のルートフィールドを想像してください：

```graphql
{
  username(username: "zuck") {
    id
  }
}
```

might return:

```json
{
  "username": {
    "id": "4"
  }
}
```

明らかに、レスポンス内のオブジェクト（ID 4のユーザー）を、ユーザー名「zuck」でオブジェクトを識別するリクエストとリンクできます。次に、ユーザー名のリストを受け取り、オブジェクトのリストを返す`usernames`という名前のルートフィールドを想像してください：

```graphql
{
  usernames(usernames: ["zuck", "moskov"]) {
    id
  }
}
```

might return:

```json
{
  "usernames": [
    {
      "id": "4"
    },
    {
      "id": "6"
    }
  ]
}
```

クライアントがユーザー名をレスポンスにリンクできるようにするには、レスポンス内の配列が引数として渡された配列と同じサイズであり、レスポンス内の順序が引数の順序と一致する必要があることを知る必要があります。これらを_複数形の識別ルートフィールド_と呼び、それらの要件は以下に説明されています。

### フィールド

この仕様に準拠するサーバーは、入力引数のリストを受け入れ、レスポンスのリストを返すルートフィールドを公開する場合があります。仕様に準拠するクライアントがこれらのフィールドを使用するには、これらのフィールドは_複数形の識別ルートフィールド_である必要があり、次の要件に従う必要があります。

注意：仕様に準拠するサーバーは、_複数形の識別ルートフィールド_ではないルートフィールドを公開する場合があります。仕様に準拠するクライアントは、クエリでこれらのフィールドをルートフィールドとして使用できません。

_複数形の識別ルートフィールド_は、単一の引数を持つ必要があります。その引数の型は、非nullの非nullリストである必要があります。`usernames`の例では、フィールドは`usernames`という名前の単一の引数を受け取り、その型（型システムの省略形を使用）は`[String!]!`になります。

_複数形の識別ルートフィールド_の戻り値の型は、リスト、またはリストをラップする非nullラッパーである必要があります。リストは、`Node`インターフェース、`Node`インターフェースを実装するオブジェクト、またはそれらの型をラップする非nullラッパーをラップする必要があります。

_複数形の識別ルートフィールド_が使用されるたびに、レスポンス内のリストの長さは、引数内のリストの長さと同じである必要があります。レスポンス内の各項目は、入力内のその項目に対応する必要があります。より正式には、ルートフィールドに入力リスト`Lin`を渡すと出力値`Lout`が得られる場合、任意の順列`P`について、ルートフィールドに`P(Lin)`を渡すと、出力値`P(Lout)`が得られる必要があります。

このため、サーバーは、レスポンス型を非nullラッパーでラップしないことをお勧めします。入力内の特定のエントリのオブジェクトを取得できない場合でも、その入力エントリの出力に値を提供する必要があるためです。`null`は、これを行うための有用な値です。
