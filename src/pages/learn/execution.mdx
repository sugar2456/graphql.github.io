# 実行

<p className="learn-subtitle">GraphQLがリクエストされたフィールドにデータを提供する方法を学ぶ</p>

解析されたドキュメントが[検証](/learn/validation/)された後、クライアントのリクエストはGraphQLサーバーによって[実行](https://spec.graphql.org/draft/#sec-Execution)され、返される結果はリクエストされたクエリの形状を反映します。このページでは、クライアントがリクエストしたフィールドに応じて、既存のソースからデータを読み取ったり、既存のソースにデータを書き込んだりするGraphQL操作の実行フェーズについて学びます。

## フィールドリゾルバ

GraphQLは型システムなしでは操作を実行できないため、クエリの実行を説明するためにサンプル型システムを使用しましょう。これは、このガイド全体の例で使用されている同じ型システムの一部です：

```graphql
type Query {
  human(id: ID!): Human
}

type Human {
  name: String
  appearsIn: [Episode]
  starships: [Starship]
}

enum Episode {
  NEWHOPE
  EMPIRE
  JEDI
}

type Starship {
  name: String
}
```

クエリが実行されるときに何が起こるかを説明するために、例を見てみましょう：

```graphql
# { "graphiql": true }
query {
  human(id: 1002) {
    name
    appearsIn
    starships {
      name
    }
  }
}
```

GraphQLクエリの各フィールドは、次の型を返す前の型の関数またはメソッドとして考えることができます。これがまさにGraphQLの動作方法です—各型の各フィールドは、GraphQLサーバー開発者によって記述された_リゾルバ関数_によってサポートされています。フィールドが実行されると、対応するリゾルバが呼び出されて次の値が生成されます。

フィールドが文字列や数値のようなスカラー値を生成する場合、実行は完了します。しかし、フィールドがオブジェクト値を生成する場合、クエリにはそのオブジェクトに適用される別のフィールドの選択が含まれます。これはリーフ値に到達するまで続きます。GraphQLクエリは常にスカラー型または列挙型で終わります。

## ルートフィールドとリゾルバ

すべてのGraphQLサーバーの最上位には、GraphQL APIへの可能なエントリーポイントを表すオブジェクト型があり、これはしばしば「`query`ルート操作型」または`Query`型と呼ばれます。APIがデータを書き込むためのミューテーションとリアルタイムデータを取得するためのサブスクリプションもサポートしている場合、これらの種類の操作を実行するためのフィールドを公開する`Mutation`型と`Subscription`型も持つことになります。これらの型について詳しくは、[スキーマと型のページ](/learn/schema/#the-query-mutation-and-subscription-types)をご覧ください。

この例では、`Query`型は`id`引数を受け入れる`human`というフィールドを提供しています。このフィールドのリゾルバ関数は、おそらくデータベースにアクセスしてから`Human`型を構築して返します：

```js
function resolveHumanQuery(obj, args, context, info) {
  return context.db.loadHumanByID(args.id).then(userData => new Human(userData));
}
```

この例はJavaScriptで記述されていますが、GraphQLサーバーは[多くの異なる言語](/code/)で構築できます。リファレンス実装では、リゾルバ関数は4つの引数を受け取ります：

- `obj`: 前のオブジェクト（ルート`Query`型のフィールドの場合、この引数はしばしば使用されません）。
- `args`: GraphQL操作でフィールドに提供される引数。
- `context`: すべてのリゾルバに提供される値で、現在ログインしているユーザーやデータベースへのアクセスなど、重要なコンテキスト情報を保持する場合があります。
- `info`: 一般的に高度なユースケースでのみ使用され、現在の操作に関連するフィールド固有の情報とスキーマの詳細を保持する値です。詳細については、[type GraphQLResolveInfo](/graphql-js/type/#graphqlobjecttype)を参照してください。

<Callout type="info">
クエリ操作は技術的に実行中に基盤となるデータシステムにデータを書き込むことができますが、ミューテーション操作は、実行中に副作用を生成するリクエストに従来使用されています。また、ミューテーション操作は副作用を生成するため、GraphQL実装はこれらのフィールドを順次実行することが期待されます。
</Callout>

## 非同期リゾルバ

このリゾルバ関数で何が起こっているかを詳しく見てみましょう：

```js
function resolveHuman(obj, args, context, info) {
  return context.db.loadHumanByID(args.id).then(userData => new Human(userData));
}
```

GraphQLクエリの`id`引数は、データがリクエストされているユーザーを指定し、`context`はデータベースからこのデータを取得するためのアクセスを提供します。データベースからの読み込みは非同期操作であるため、これは[Promise](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise)を返します。JavaScriptでは、Promiseは非同期値を操作するために使用されますが、同じ概念は多くの言語に存在し、しばしば_Futures_、_Tasks_、または_Deferred_と呼ばれます。データベースがデータを返すと、新しい`Human`オブジェクトを構築して返すことができます。

リゾルバ関数はPromiseを認識する必要がありますが、GraphQLクエリはそうではないことに注意してください。それは単に`human`フィールドが、さらにスカラー`name`値に解決できる何かを返すことを期待しています。実行中、GraphQLは続行する前にPromise、Futures、およびTasksが完了するのを待ち、最適な並行性でそれを行います。

## 単純なリゾルバ

`Human`オブジェクトが利用可能になったので、GraphQLの実行はこの型に対してリクエストされたフィールドで続行できます：

```js
function resolveHumanName(obj, args, context, info) {
  return obj.name;
}
```

GraphQLサーバーは、次に何をすべきかを決定するために使用される型システムによって動力を得ています。`human`フィールドが何かを返す前でも、GraphQLは次のステップが`Human`型のフィールドを解決することになるとわかっています。これは、型システムが`human`フィールドがこの出力型を返すことを伝えているためです。

この場合、名前を解決することは簡単です。名前リゾルバ関数が呼び出され、`obj`引数は前のフィールドから返された新しい`Human`オブジェクトです。この場合、このオブジェクトに`name`プロパティがあることを期待しており、それを読み取って直接返すことができます。

多くのGraphQLライブラリでは、フィールドに対してリゾルバが提供されていない場合、同じ名前のプロパティが読み取られて返されることを想定して、このような単純なリゾルバを省略できます。

## スカラー強制型変換

`name`フィールドが解決されている間、`appearsIn`フィールドと`starships`フィールドは並行して解決できます。`appearsIn`フィールドも単純なリゾルバを持つことができますが、詳しく見てみましょう：

```js
const Human = {
  appearsIn(obj) {
    return obj.appearsIn; // 例: [4, 5, 6]
  },
};
```

型システムは`appearsIn`が既知の値を持つ列挙型を返すと主張していますが、この関数は数値を返しています！確かに結果を見ると、列挙型の適切な値が返されていることがわかります。何が起こっているのでしょうか？

これは_スカラー強制型変換_の例です。型システムは何を期待すべきかを知っており、リゾルバ関数によって返された値を、API契約を維持するものに変換します。この場合、サーバー上に`4`、`5`、`6`のような数値を内部的に使用するが、GraphQL型システムでは期待される値としてそれらを表す列挙型が定義されている可能性があります。

## リストリゾルバ

上記の`appearsIn`フィールドで、フィールドがもののリストを返すときに何が起こるかの一部をすでに見ました。これは列挙型の値を含む[リスト型](/learn/schema/#lists)を返し、それが型システムが期待していたものであるため、リスト内の各項目が適切な値に強制型変換されました。`starships`フィールドが解決されるとき、何が起こるでしょうか？

```js
function resolveHumanStarships(obj, args, context, info) {
  return Promise.all(
    obj.starshipIDs.map(id =>
      context.db.loadStarshipByID(id).then(shipData => new Starship(shipData))
    )
  );
}
```

このフィールドのリゾルバは、単にPromiseを返すだけでなく、Promiseの_リスト_を返しています。`Human`オブジェクトには、彼らが操縦した`Starships`のIDのリストがありましたが、実際のStarshipオブジェクトを取得するには、それらのIDをすべて読み込む必要があります。

GraphQLは続行する前に、これらすべてのPromiseを並行して待機し、オブジェクトのリストが残ると、これらの各項目の`name`フィールドを再度並行して読み込みます。

## 結果の生成

各フィールドが解決されると、結果の値は、フィールド名（またはエイリアス）をキーとし、解決された値を値とするキー値マップに配置されます。これは、クエリの最下部のリーフフィールドから、ルート`Query`型の元のフィールドまで続きます。これらをまとめると、元のクエリを反映する構造が生成され、それを（通常はJSONとして）リクエストしたクライアントに送信できます。

これらの解決関数がどのように結果を生成するかを確認するために、元のクエリをもう一度見てみましょう：

```graphql
# { "graphiql": true }
query {
  human(id: 1002) {
    name
    appearsIn
    starships {
      name
    }
  }
}
```

ご覧のとおり、ネストされた選択セット内の各フィールドは、クエリの実行中にスカラーのリーフ値に解決されます。

## 次のステップ

実行について学んだことをまとめると：

- GraphQL型システムの各フィールドには、既存のデータソースからフィールドにデータを提供する対応するリゾルバ関数があります
- 実行は最上位の`Query`、`Mutation`、または`Subscription`フィールドから始まります
- リゾルバは非同期で実行される場合があります
- スカラー強制型変換は、値をスキーマが期待する型に変換します
- オブジェクト型のフィールドが他のオブジェクトのリスト型を返す場合、外部キーのような参照（IDなど）を関連オブジェクトに変換するために、基盤となるデータソースから追加のデータを取得する必要がある場合があります
- リクエストされたすべてのフィールドが期待されるリーフ値に解決されると、結果がクライアントに送信されます（通常はJSONとして）

操作がどのように実行されるかを理解したので、GraphQLリクエストのライフサイクルの最後の段階である[レスポンス](/learn/response/)がクライアントに配信される段階に進むことができます。
