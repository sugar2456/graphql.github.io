# レスポンス

<p className="learn-subtitle">GraphQLがクライアントにデータを返す方法を学ぶ</p>

GraphQLドキュメントが[検証](/learn/validation/)され、[実行](/learn/execution/)された後、サーバーはリクエストしたクライアントに[レスポンス](https://spec.graphql.org/draft/#sec-Response)を返します。GraphQLの強みの1つは、サーバーのレスポンスがクライアントの元のリクエストの形状を反映することですが、操作の実行前または実行中に予期しないことが発生した場合、レスポンスには有用な情報も含まれる場合があります。このページでは、GraphQLリクエストのライフサイクルのこの最終フェーズについて詳しく説明します。

## データ

このガイド全体の例で見たように、GraphQLリクエストが実行されると、レスポンスは最上位の`data`キーで返されます。例えば：

```graphql
# { "graphiql": true }
query {
  human(id: 1002) {
    name
    appearsIn
    starships {
      name
    }
  }
}
```

`data`キーの包含は、基盤となるGraphQL実装によって行われた任意の決定ではありません—これは[GraphQL仕様](https://spec.graphql.org/draft/#sec-Data)によって記述されています。このキーの下に、リクエストされた操作の実行結果が見つかります。一部のフィールドリゾルバの実行中にエラーが発生した場合、リクエストされたフィールドの部分的なデータが含まれる場合があります。

GraphQL仕様が要求していないことの1つは、レスポンスの特定のシリアル化形式です。とはいえ、上記の例のように、レスポンスは通常JSONとしてフォーマットされます。

さらに、GraphQL仕様は、リクエストに特定のトランスポートプロトコルの使用を要求していませんが、ステートレスなクエリとミューテーション操作には[HTTPが一般的に使用されます](/learn/serving-over-http/)。長期間にわたるステートフルなサブスクリプション操作は、代わりにWebSocketまたはサーバー送信イベントによってサポートされることがよくあります。

<Callout type="info">
GraphQLクライアントとサーバーでHTTPを使用するための追加のガイドラインを含む[GraphQL over HTTP仕様のドラフト](https://graphql.github.io/graphql-over-http/draft/)が利用可能です。
</Callout>

## エラー

`data`キーに加えて、GraphQL仕様は、レスポンスで[エラー](https://spec.graphql.org/draft/#sec-Errors)をどのようにフォーマットするかを概説しています。GraphQL実装がレスポンスでエラー情報とともに部分的なデータを提供するかどうかは、発生したエラーの種類によって異なります。GraphQLリクエストのライフサイクル中に発生する可能性のあるさまざまな種類のエラーを見てみましょう。

### リクエストエラー

リクエストエラーは、通常、クライアントが間違いを犯したために発生します。例えば、ドキュメントに_構文エラー_がある可能性があります。欠落している括弧や、未知のルート操作型キーワードの使用などです：

{/* <!-- snippet-ignore --> */}
```graphql
# { "graphiql": true }
operation { 
  updateHumanName(id: "1000", name: "Luke Starkiller" ) {
    id
    name
  }
}
```

`errors`オブジェクト内の`message`キーは、開発者が発生したエラーの種類を理解するのに役立つ情報を提供し、`locations`キー（存在する場合）は、ドキュメント内でエラーが発生した場所を示します。

場合によっては、GraphQLリクエストが構文的に正しい場合でも、サーバーがドキュメントを解析してスキーマに対して[検証](/learn/validation/)すると、操作の一部に問題が見つかり、_検証エラー_が発生する可能性があります。

例えば、クライアントが`Starship`型に存在しないフィールドをリクエストする場合があります：

```graphql
# { "graphiql": true }
query {
  starship(id: 3000) {
    width
  }
}
```

クライアントが対応するフィールド引数に対して間違った変数型を指定した場合にも、検証エラーが発生します：

```graphql
# { "graphiql": true, "variables": { "ep": "JEDI" } }
query HeroForEpisode($ep: String!) {
  hero(episode: $ep) {
    name
  }
}
```

前の例では、リクエストエラーが発生した場合、フィールドリゾルバが実行される前にサーバーがクライアントにエラーレスポンスを返すため、`data`キーは含まれないことがわかります。

### フィールドエラー

実行中に予期しないことが発生した場合、フィールドエラーが発生します。例えば、リゾルバが直接エラーを発生させる可能性があるか、非null出力型を持つフィールドに対してnull値などの無効なデータを返す可能性があります。

これらの場合、GraphQLは他のフィールドの実行を続行しようとし、`data`キーが`errors`キーと一緒に表示される部分的なレスポンスを返します。

例を見てみましょう：

```graphql
# { "graphiql": true }
mutation {
  firstShip: deleteStarship(id: "3001")
  secondShip: deleteStarship(id: "3010")
}
```

上記のミューテーションは、1つの操作で2つの宇宙船を削除しようとしますが、IDが`3010`の宇宙船は存在しないため、サーバーはエラーをスローします。レスポンスでは、`secondShip`としてエイリアスされたフィールドで発生したエラーに関する情報を確認できます。`data`キーの下では、最初の宇宙船のIDが正常な削除を示すために返されたのに対し、2番目の宇宙船は、そのリゾルバ関数で発生したエラーによりnull結果を生成したことも確認できます。

### ネットワークエラー

あらゆる種類のAPIへのネットワーク呼び出しと同様に、GraphQLに固有ではないネットワークエラーが、リクエスト中の任意の時点で発生する可能性があります。これらの種類のエラーは、リクエストが完了する前にクライアントとサーバー間の通信をブロックします。SSLエラーや接続タイムアウトなどです。選択したGraphQLサーバーとクライアントライブラリに応じて、失敗した操作の再試行など、特別なネットワークエラー処理をサポートする機能が組み込まれている場合があります。

## 拡張機能

GraphQL仕様がレスポンスで許可する最後の最上位キーは`extensions`キーです。このキーは、GraphQL実装がレスポンスに関する追加情報を提供するために予約されており、存在する場合はオブジェクトである必要がありますが、含まれる内容に関する他の制限はありません。

例えば、一部のGraphQLサーバーは、このキーの下にテレメトリーデータやレート制限の消費に関する情報を含める場合があります。`extensions`で利用可能なデータと、このデータが本番環境または開発環境で利用可能かどうかは、特定のGraphQL実装に完全に依存することに注意してください。

## 次のステップ

GraphQLレスポンス形式について学んだことをまとめると：

- GraphQL仕様では、レスポンスに3つの最上位キーが許可されています：`data`、`errors`、および`extensions`
- `data`または`errors`の少なくとも1つがレスポンスに存在します（両方を含む場合は「部分的なレスポンス」です）
- `data`キーには、実行された操作の結果が含まれます
- 発生したエラーに関する情報は、レスポンスの`errors`キーに含まれます
- リクエストエラー（構文エラーや検証エラーなど）は、実行が開始される前に発生するため、`data`はレスポンスに含まれません
- 実行中にフィールドエラーが発生した場合、`errors`キーに問題の説明があり、`data`キーに部分的なデータが含まれる場合があります
- GraphQL実装は、`extensions`キーにレスポンスに関する追加の任意の情報を含める場合があります

GraphQLリクエストの異なるフェーズと、レスポンスがクライアントに提供される方法を理解したので、[イントロスペクション](/learn/introspection)ページに進んで、GraphQLサーバーが独自のスキーマに関する情報をクエリする方法について学んでください。
