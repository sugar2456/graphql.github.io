# スキーマと型

<p className="learn-subtitle">GraphQL型システムの異なる要素について学ぶ</p>

GraphQLの[型システム](https://spec.graphql.org/draft/#sec-Type-System)は、APIからクエリできるデータを記述します。これらの機能のコレクションは、サービスの_スキーマ_と呼ばれ、クライアントはそのスキーマを使用して、予測可能な結果を返すクエリをAPIに送信できます。

このページでは、GraphQLの[6種類の名前付き型定義](https://spec.graphql.org/draft/#sec-Types)と、型システムの他の機能について説明し、それらを使用してデータとそれらの間の関係を記述する方法を学びます。GraphQLは任意のバックエンドフレームワークまたはプログラミング言語で使用できるため、実装固有の詳細を避け、概念についてのみ説明します。

## 型システム

以前にGraphQLクエリを見たことがある場合、GraphQLクエリ言語は基本的にオブジェクト上のフィールドを選択することであることがわかります。したがって、例えば、次のクエリでは：

```graphql
# { "graphiql": true }
{
  hero {
    name
    appearsIn
  }
}
```

1. 特別な「ルート」オブジェクトから始めます
2. その上で`hero`フィールドを選択します
3. `hero`によって返されたオブジェクトについて、`name`と`appearsIn`フィールドを選択します

GraphQLクエリの形状は結果と密接に一致するため、サーバーについてそれほど知らなくても、クエリが何を返すかを予測できます。しかし、リクエストできるデータの正確な説明があると便利です。例えば、どのフィールドを選択できますか？それらはどのような種類のオブジェクトを返す可能性がありますか？それらのサブオブジェクトでどのフィールドが利用可能ですか？

そこでスキーマが登場します。すべてのGraphQLサービスは、そのサービスでクエリできる可能なデータのセットを完全に記述する型のセットを定義します。その後、リクエストが到着すると、それらはそのスキーマに対して検証され、実行されます。

## 型言語

GraphQLサービスは任意の言語で記述でき、スキーマで型を定義する際に取ることができる多くの異なるアプローチがあります：

- 一部のライブラリでは、GraphQL実装の記述に使用されたのと同じプログラミング言語を使用して、スキーマ型、フィールド、リゾルバ関数を一緒に構築します。
- 一部のライブラリでは、一般的にスキーマ定義言語（SDL）と呼ばれるものを使用して型とフィールドをより人間工学的に定義し、対応するフィールドのリゾルバ関数を別々に記述できます。
- 一部のライブラリでは、リゾルバ関数を記述して注釈を付け、そこからスキーマを推論できます。
- 一部のライブラリでは、基盤となるデータソースに基づいて、型とリゾルバ関数の両方を推論することさえできます。

このガイドでGraphQLスキーマについて説明する際に特定のプログラミング言語に依存できないため、SDLを使用します。これは、これまでに見てきたクエリ言語に似ており、言語に依存しない方法でGraphQLスキーマについて話すことを可能にするためです。

## オブジェクト型とフィールド

GraphQLスキーマの最も基本的なコンポーネントは[オブジェクト型](https://spec.graphql.org/draft/#sec-Objects)です。これは、サービスから取得できるオブジェクトの種類と、それが持つフィールドを表します。SDLでは、次のように表します：

```graphql
type Character {
  name: String!
  appearsIn: [Episode!]!
}
```

言語は読みやすいですが、共通の語彙を持つために説明しましょう：

- `Character`は[GraphQLオブジェクト型](#object-types-and-fields)で、いくつかのフィールドを持つ型を意味します。スキーマ内の型のほとんどはオブジェクト型になります。
- `name`と`appearsIn`は`Character`型の[フィールド](#object-types-and-fields)です。これは、`name`と`appearsIn`が、`Character`型で動作するGraphQLクエリの任意の部分に表示できる唯一のフィールドであることを意味します。
- `String`は組み込みの[スカラー型](#scalar-types)の1つです。これらは、単一のスカラー値に解決され、クエリでサブ選択を持つことができない型です。スカラー型については後で詳しく説明します。
- `String!`は、フィールドが[非null型](#non-null)であることを意味します。つまり、GraphQLサービスは、このフィールドをクエリするたびに値を提供することを約束します。SDLでは、感嘆符でそれらを表します。
- `[Episode!]!`は`Episode`オブジェクトの[リスト型](#list)を表します。リストが非nullの場合、`appearsIn`フィールドをクエリするときは常に配列（0個以上のアイテム）を期待できます。この場合、`Episode!`もリスト内で非nullであるため、配列内のすべてのアイテムが常に`Episode`オブジェクトであることを期待できます。

これで、GraphQLオブジェクト型がどのように見えるか、およびSDLの基本を読み取る方法がわかりました。

### 引数

GraphQLオブジェクト型のすべてのフィールドは、0個以上の[引数](https://spec.graphql.org/draft/#sec-Field-Arguments)を持つことができます。例えば、以下の`length`フィールド：

```graphql
type Starship {
  id: ID!
  name: String!
  length(unit: LengthUnit = METER): Float
}
```

すべての引数には名前が付けられます。JavaScriptやPythonなどの関数が順序付き引数のリストを受け取る言語とは異なり、GraphQLのすべての引数は名前で具体的に渡されます。この場合、`length`フィールドには`unit`という名前の定義された引数が1つあります。

引数は必須またはオプションのいずれかです。引数がオプションの場合、_デフォルト値_を定義できます。`unit`引数が渡されない場合、デフォルトで`METER`に設定されます。

### Query、Mutation、Subscription型

すべてのGraphQLスキーマは`query`操作をサポートする必要があります。この[ルート操作型](https://spec.graphql.org/draft/#sec-Root-Operation-Types)の_エントリーポイント_は、デフォルトで`Query`という名前の通常のオブジェクト型です。したがって、次のようなクエリを見た場合：

```graphql
# { "graphiql": true }
{
  droid(id: "2000") {
    name
  }
}
```

これは、GraphQLサービスに`droid`フィールドを持つ`Query`型が必要であることを意味します：

```graphql
type Query {
  droid(id: ID!): Droid
}
```

スキーマは、追加の`Mutation`型と`Subscription`型を追加し、対応するルート操作型にフィールドを定義することで、`mutation`操作と`subscription`操作もサポートする場合があります。

スキーマへのエントリーポイントであるという特別なステータスを除いて、`Query`、`Mutation`、および`Subscription`型は、他のGraphQLオブジェクト型と同じであり、それらのフィールドはまったく同じように機能することを覚えておくことが重要です。

ルート操作型に異なる名前を付けることもできます。そうすることを選択した場合、`schema`キーワードを使用してGraphQLに新しい名前を通知する必要があります：

```graphql
schema {
  query: MyQueryType
  mutation: MyMutationType
  subscription: MySubscriptionType
}
```

## スカラー型

GraphQLオブジェクト型には名前とフィールドがありますが、ある時点で、それらのフィールドは何らかの具体的なデータに解決される必要があります。そこで[スカラー型](https://spec.graphql.org/draft/#sec-Scalars)が登場します：それらはクエリのリーフ値を表します。

次のクエリでは、`name`と`appearsIn`フィールドはスカラー型に解決されます：

```graphql
# { "graphiql": true }
{
  hero {
    name
    appearsIn
  }
}
```

これらのフィールドにはサブフィールドがないため、これがわかります—それらはクエリのリーフです。

GraphQLには、すぐに使用できる[デフォルトのスカラー型](https://spec.graphql.org/draft/#sec-Scalars.Built-in-Scalars)のセットが付属しています：

- `Int`: 符号付き32ビット整数。
- `Float`: 符号付き倍精度浮動小数点値。
- `String`: UTF-8文字シーケンス。
- `Boolean`: `true`または`false`。
- `ID`: 一意の識別子。オブジェクトを再取得したり、キャッシュのキーとして使用されることがよくあります。`ID`型は`String`と同じ方法でシリアル化されます。ただし、`ID`として定義することは、人間が読めることを意図していないことを示します。

ほとんどのGraphQLサービス実装では、カスタムスカラー型を指定する方法もあります。例えば、`Date`型を定義できます：

```graphql
scalar Date
```

その後、その型をシリアル化、逆シリアル化、検証する方法を定義するのは実装次第です。例えば、`Date`型が常に整数タイムスタンプにシリアル化されることを指定でき、クライアントは任意の日付フィールドに対してその形式を期待することを知る必要があります。

## 列挙型

[列挙型](https://spec.graphql.org/draft/#sec-Enums)は、列挙型としても知られており、特定の許可された値のセットに制限された特殊な種類のスカラーです。これにより、以下が可能になります：

1. この型の引数が許可された値の1つであることを検証する
2. フィールドが常に有限の値のセットの1つになることを型システムを通じて伝達する

SDLでの列挙型定義の例を次に示します：

```graphql
enum Episode {
  NEWHOPE
  EMPIRE
  JEDI
}
```

これは、スキーマで`Episode`型を使用する場所では、`NEWHOPE`、`EMPIRE`、または`JEDI`のいずれかであることを期待することを意味します。

<Callout type="info">さまざまな言語でのGraphQLサービス実装には、列挙型を処理するための言語固有の方法があります。列挙型を第一級市民としてサポートする言語では、実装がそれを活用する場合があります。列挙型サポートがないJavaScriptのような言語では、これらの値は内部的に整数のセットにマッピングされる場合があります。ただし、これらの詳細はクライアントに漏れず、クライアントは列挙型の値の文字列名の観点から完全に操作できます。</Callout>

## 型修飾子

GraphQLでは、型はデフォルトでnull許容および単数であると見なされます。ただし、スキーマ（または[クエリ変数宣言](/learn/queries/#variables)）でこれらの名前付き型を使用する場合、それらの値の意味に影響を与える追加の_型修飾子_を適用できます。

上記のオブジェクト型の例で見たように、GraphQLは2つの型修飾子—[リスト](https://spec.graphql.org/draft/#sec-List)と[非null](https://spec.graphql.org/draft/#sec-Non-Null)型—をサポートし、それらは個別に、または互いに組み合わせて使用できます。

### 非null

例を見てみましょう：

```graphql
type Character {
  name: String!
}
```

ここでは、`String`型を使用し、型名の後に感嘆符（`!`）を追加することで、それを非null型としてマークしています。これは、サーバーがこのフィールドに対して常に非null値を返すことを期待することを意味し、リゾルバがnull値を生成した場合、GraphQL実行エラーがトリガーされ、クライアントに何かが間違っていることを知らせます。

上記の例で見たように、非null型修飾子は、フィールドの引数を定義する際にも使用でき、その引数としてnull値が渡された場合、GraphQLサーバーが検証エラーを返すことになります：

```graphql
# { "graphiql": true }
{
  droid(id: null) {
    name
  }
}
```

### リスト

リストも同様に機能します。型修飾子を使用して型をリスト型としてマークできます。これは、このフィールドがその型の配列を返すことを示します。SDLでは、型を角括弧`[`と`]`で囲むことで表されます。引数でも同じように機能し、検証ステップでその値に対して配列が期待されます。例を次に示します：

```graphql
type Character {
  name: String!
  appearsIn: [Episode]!
}
```

上記で見たように、非nullとリストの修飾子は組み合わせることができます。例えば、非null`String`型のリストを持つことができます：

{/* <!-- snippet-ignore --> */}
```graphql
myField: [String!]
```

これは、_リスト自体_がnullになる可能性があるが、nullメンバーを持つことができないことを意味します。例えば、JSONでは：

```js
myField: null // 有効
myField: [] // 有効
myField: ["a", "b"] // 有効
myField: ["a", null, "b"] // エラー
```

次に、`String`型の非nullリストを定義したとしましょう：

{/* <!-- snippet-ignore --> */}
```graphql
myField: [String]!
```

これは、リスト自体がnullになることはできないが、null値を含むことができることを意味します：

```js
myField: null // エラー
myField: [] // 有効
myField: ["a", "b"] // 有効
myField: ["a", null, "b"] // 有効
```

最後に、非null`String`型の非nullリストを持つこともできます：

{/* <!-- snippet-ignore --> */}
```graphql
myField: [String!]!
```

これは、リストがnullになることはできず、null値を含むこともできないことを意味します：

```js
myField: null // エラー
myField: [] // 有効
myField: ["a", "b"] // 有効
myField: ["a", null, "b"] // エラー
```

必要に応じて、任意の数の非nullとリストの修飾子を任意にネストできます。

<Callout type="info">GraphQLでは、非空のリストが提供された場合にのみフィールドのデータが有効と見なされる型を定義する方法はありません。言い換えれば、`[]`は非null型の非nullリストに対して依然として有効なレスポンスです。</Callout>

## インターフェース型

多くの型システムと同様に、GraphQLは_抽象型_をサポートしています。探索する最初の型は[インターフェース型](https://spec.graphql.org/draft/#sec-Interfaces)で、それを実装するために具体的なオブジェクト型または他のインターフェース型も含める必要がある特定のフィールドのセットを定義します。

例えば、スター・ウォーズ三部作の任意のキャラクターを表す`Character`インターフェース型を持つことができます：

```graphql
interface Character {
  id: ID!
  name: String!
  friends: [Character]
  appearsIn: [Episode]!
}
```

これは、`Character`を_実装_する任意の型が、同じ引数と戻り値の型と同様に、これらの正確なフィールドを持つ必要があることを意味します。

例えば、`Character`を実装する可能性のある型を次に示します：

```graphql
type Human implements Character {
  id: ID!
  name: String!
  friends: [Character]
  appearsIn: [Episode]!
  starships: [Starship]
  totalCredits: Int
}

type Droid implements Character {
  id: ID!
  name: String!
  friends: [Character]
  appearsIn: [Episode]!
  primaryFunction: String
}
```

これらの型の両方が`Character`インターフェース型のすべてのフィールドを持っているだけでなく、その特定の種類のキャラクターに固有の追加フィールド—`totalCredits`、`starships`、`primaryFunction`—も持っていることがわかります。

インターフェース型は、オブジェクトまたはオブジェクトのセットを返したいが、それらがいくつかの異なる型である可能性がある場合に有用です。例えば、次のクエリがエラーを生成することに注意してください：

```graphql
# { "graphiql": true }
{
  hero(episode: JEDI) {
    name
    primaryFunction
  }
}
```

`hero`フィールドは`Character`型を返します。これは、`episode`引数に応じて`Human`または`Droid`のいずれかである可能性があることを意味します。上記のクエリでは、`Character`インターフェース型に存在するフィールドのみを要求できます。これには`primaryFunction`は含まれません。

特定のオブジェクト型のフィールドを要求するには、[インラインフラグメント](/learn/queries/#inline-fragments)を使用する必要があります：

```graphql
# { "graphiql": true }
{
  hero(episode: JEDI) {
    name
    ... on Droid {
      primaryFunction
    }
  }
}
```

インターフェース型は、他のインターフェース型を実装することもできます：

```graphql
interface Node {
  id: ID!
}

interface Character implements Node {
  id: ID!
  name: String!
  friends: [Character]
  appearsIn: [Episode]!
}
```

インターフェース型は、それ自体を実装したり、互いに循環参照を含むことはできないことに注意してください。

<Callout type="info">GraphQL APIで型が共通のフィールドを共有する場合でも、それらのフィールドが一貫して名前付けされたままであることを強制するためにインターフェース型の使用を常に保証するわけではありません。インターフェース型は、それらを実装する型間で共有される動作を示す強力な方法です。使用する場合、それらはクライアント開発者にとって意味的に意味がある必要があり、`Character`が人間とドロイドにとって有用な抽象化であるのと同じように意味がある必要があります。</Callout>

## Union型

GraphQLは、[Union型](https://spec.graphql.org/draft/#sec-Unions)と呼ばれる2番目の抽象型をサポートしています。Union型はインターフェース型と類似点を共有していますが、構成型間で共有フィールドを定義することはできません。

Union型は、そのメンバーオブジェクト型を示すことで定義されます：

```graphql
union SearchResult = Human | Droid | Starship
```

スキーマで`SearchResult`型を返す場所では、`Human`、`Droid`、または`Starship`を取得する可能性があります。Union型のメンバーは具体的なオブジェクト型である必要があることに注意してください。インターフェース型や他のUnion型をメンバーとして使用して定義することはできません。

この場合、`SearchResult` Union型を返すフィールドをクエリする場合、メンバーオブジェクト型で定義されているフィールドをクエリできるようにするために[インラインフラグメント](/learn/queries/#inline-fragments)を使用する必要があります：

```graphql
# { "graphiql": true}
{
  search(text: "an") {
    __typename
    ... on Human {
      name
      height
    }
    ... on Droid {
      name
      primaryFunction
    }
    ... on Starship {
      name
      length
    }
  }
}
```

`__typename`フィールドは、すべてのオブジェクト型に自動的に存在し、その型の名前に解決される特別な_メタフィールド_で、クライアントでデータ型を区別する方法を提供します。

また、この場合、`Human`と`Droid`が共通のインターフェース（`Character`）を共有しているため、1つの場所でそれらの共通フィールドをクエリし、同じ結果を取得できます：

```graphql
# { "graphiql": true}
{
  search(text: "an") {
    __typename
    ... on Character {
      name
    }
    ... on Human {
      height
    }
    ... on Droid {
      primaryFunction
    }
    ... on Starship {
      name
      length
    }
  }
}
```

`Starship`は`Character`ではないため、`name`が`Starship`でまだ指定されていることに注意してください。そうでない場合、結果に表示されません！

## 入力オブジェクト型

このページで説明した例のほとんどは、オブジェクト、スカラー、列挙、インターフェース、Union型がスキーマ内のフィールドの_出力型_としてどのように使用できるかを示しています。しかし、フィールド引数は_入力型_を指定する必要があることも見てきました。

これまで、フィールド引数の入力型としてスカラー値（列挙型やString型など）のみを使用することについて説明してきました。ただし、[入力オブジェクト型](https://spec.graphql.org/draft/#sec-Input-Objects)を使用して、複雑なオブジェクトを引数として渡すこともできます。これは、探索するGraphQLの最後の種類の名前付き型です。

これは、[ミューテーション](/learn/mutations/)の場合に特に価値があります。作成するオブジェクト全体を渡したい場合があります。SDLでは、入力オブジェクト型は通常のオブジェクト型と似ていますが、`type`の代わりに`input`キーワードを使用します：

```graphql
input ReviewInput {
  stars: Int!
  commentary: String
}

type Mutation {
  createReview(episode: Episode, review: ReviewInput!): Review
}
```

ミューテーションで入力オブジェクト型を使用する方法を次に示します：

```graphql
# { "graphiql": true }
mutation {
  createReview(
    episode: JEDI, 
    review: {
      stars: 5
      commentary: "This is a great movie!"
    }
  ) {
    stars
    commentary
  }
}
```

入力オブジェクト型のフィールドは、他の入力オブジェクト型を参照できますが、スキーマで入力型と出力型を混在させることはできません。入力オブジェクト型のフィールドに引数を持つこともできません。

## ディレクティブ

フィールド引数が不十分な場合や、特定の共通の動作を複数の場所で複製する必要がある場合、[ディレクティブ](https://spec.graphql.org/draft/#sec-Type-System.Directives)により、`@`文字の後にディレクティブの名前を続けることで、GraphQLスキーマまたは操作の一部を変更できます。

_型システムディレクティブ_により、スキーマ内の型、フィールド、引数に注釈を付けて、それらが異なる方法で検証または実行されるようにできます。

<Callout type="info">
ディレクティブは、GraphQL操作で使用するために_executable directives_として定義することもできます。[クエリページで実行可能ディレクティブについて詳しく読む。](/learn/queries/#directives)
</Callout>

GraphQL仕様は、いくつかの[組み込みディレクティブ](https://spec.graphql.org/draft/#sec-Type-System.Directives.Built-in-Directives)を定義しています。例えば、SDLをサポートする実装では、`@deprecated`ディレクティブがスキーマの非推奨部分に注釈を付けるために利用可能になります：

```graphql
type User {
  fullName: String
  name: String @deprecated(reason: "Use `fullName`.")
}
```

SDLをサポートするGraphQL実装を使用している場合、スキーマで`@deprecated`ディレクティブを明示的に定義する必要はありませんが、その基盤となる定義は次のようになります：

```graphql
directive @deprecated(
  reason: String = "No longer supported"
) on FIELD_DEFINITION | ENUM_VALUE
```

フィールドと同様に、ディレクティブは引数を受け入れることができ、それらの引数にはデフォルト値を持つことができることに注意してください。`@deprecated`ディレクティブには、`String`を入力型として受け入れるnull許容の`reason`引数があり、`"No longer supported"`にフォールバックします。ディレクティブでは、`@deprecated`ディレクティブの`FIELD_DEFINITION`や`ENUM_VALUE`など、それらが使用できる場所を指定する必要があります。

GraphQLの組み込みディレクティブに加えて、独自の_カスタムディレクティブ_を定義できます。カスタムスカラー型と同様に、クエリ実行中にカスタムディレクティブを処理する方法を決定するのは、選択したGraphQL実装次第です。

## ドキュメント

### 説明

GraphQLでは、スキーマ内の型、フィールド、引数にドキュメントを追加できます。実際、GraphQL仕様では、型、フィールド、または引数の名前が自己説明的でない限り、すべての場合でこれを行うことを推奨しています。スキーマの説明はMarkdown構文を使用して定義され、複数行または単一行にすることができます。

SDLでは、次のようになります：

```graphql
"""
スター・ウォーズの世界からのキャラクター
"""
type Character {
  "キャラクターの名前。"
  name: String!
}

"""
スター・ウォーズ三部作のエピソード
"""
enum Episode {
  "スター・ウォーズ エピソードIV：新たなる希望、1977年公開。" 
  NEWHOPE
  "スター・ウォーズ エピソードV：帝国の逆襲、1980年公開。"
  EMPIRE
  "スター・ウォーズ エピソードVI：ジェダイの帰還、1983年公開。"
  JEDI
}

"""
クエリ型、オブジェクトグラフへのすべてのエントリーポイントを表します
"""
type Query {
  """
  指定されたスター・ウォーズ映画のヒーローを取得します。
  """
  hero(
    "ヒーローが登場する映画の名前。"
    episode: Episode
  ): Character
}
```

GraphQL APIスキーマをより表現力豊かにするだけでなく、説明は[イントロスペクションクエリ](/learn/introspection/)で利用可能であり、[GraphiQL](https://github.com/graphql/graphiql)などの開発者ツールで表示されるため、クライアント開発者にとって有用です。

### コメント

場合によっては、型、フィールド、または引数を説明せず、クライアントに表示されることを意図していないスキーマにコメントを追加する必要がある場合があります。そのような場合、テキストの前に`#`文字を付けることで、SDLに単一行のコメントを追加できます：

```graphql
# この行は空白として扱われ、GraphQLによって無視されます
type Character {
  name: String!
}
```

コメントはクライアントクエリにも追加できます：

```graphql
# { "graphiql": true }
{
  hero {
    name
    # クエリにはコメントを含めることができます！
    friends {
      name
    }
  }
}
```

## 次のステップ

スキーマと型について学んだことをまとめると：

- GraphQLサービスを構築するために選択されたライブラリに応じて、SDLを使用して言語に依存しない方法でスキーマを定義するか、フィールドにデータを提供するコードからスキーマをコンパイルできます
- GraphQLには6種類の名前付き型定義があります：オブジェクト、スカラー、列挙、インターフェース、Union、入力オブジェクト型
- オブジェクト型には出力型を指定するフィールドが含まれ、それらのフィールドには入力型を指定する引数がある場合があります
- `Int`、`Float`、`String`、`Boolean`、`ID`スカラー型はGraphQLに組み込まれており、独自のカスタムスカラーを定義することもできます
- スカラー型と同様に、列挙型はGraphQLスキーマのリーフ値を表しますが、有限の値のセットに制限されています
- リスト（`[]`）と非null（`!`）の型修飾子により、フィールドの出力型または引数の入力型のデフォルトの動作を変更できます
- インターフェース型とUnion型は抽象型で、単一のフィールドから異なる具体的なオブジェクト型を出力できるようにします
- 入力オブジェクト型により、スカラー型と列挙型が許可するよりも複雑な値をフィールド引数またはディレクティブ引数に渡すことができます
- 型システムディレクティブは、スキーマ内の型、フィールド、引数に適用して、クエリ中にそれらが検証または実行される方法を変更できます
- GraphQLは、型、フィールド、引数の説明を使用したスキーマドキュメントをサポートし、パーサーによって無視されるコメントもサポートします

型システムの主要な機能を理解したので、[GraphQL APIからデータをクエリする](/learn/queries/)方法について詳しく学ぶ準備ができました。
