# ミューテーション

<p className="learn-subtitle">GraphQLサーバーでデータを変更する方法を学ぶ</p>

GraphQLの議論のほとんどはデータ取得に焦点を当てていますが、完全なデータプラットフォームには、サーバー側のデータを変更する方法も必要です。

RESTでは、あらゆるリクエストがサーバー上で何らかの副作用を引き起こす可能性がありますが、慣例により、データを変更するために`GET`リクエストを使用しないことが推奨されています。GraphQLも同様です—技術的には、あらゆるフィールドリゾルバをデータ書き込みを引き起こすように実装できます—しかし、[GraphQL仕様では](https://spec.graphql.org/draft/#sel-GANRNDAB6DBmMn6D)、「最上位のミューテーションフィールド以外のフィールドの解決は、常に副作用がなく、べき等でなければならない」と述べています。したがって、仕様に準拠したGraphQLスキーマでは、ミューテーション操作の最上位フィールドのみが副作用を引き起こすことが許可されています。

このページでは、GraphQLを使用してミューテーション操作でデータを書き込む方法を学び、クライアントのユースケースをサポートする方法でそれを行います。

<Callout type="info">
クエリに適用されるGraphQL操作のすべての機能は、ミューテーションにも適用されるため、先に進む前に[クエリ](/learn/queries/)ページを確認してください。
</Callout>

## 新しいデータの追加

REST APIで新しいデータを作成する場合、特定のエンドポイントに`POST`リクエストを送信し、リクエストの本文に作成するエンティティに関する情報を含めます。GraphQLは異なるアプローチを取ります。

スキーマで定義されているミューテーションの例を見てみましょう：

```graphql
enum Episode {
  NEWHOPE
  EMPIRE
  JEDI
}

input ReviewInput {
  stars: Int!
  commentary: String
}

type Mutation {
  createReview(episode: Episode, review: ReviewInput!): Review
}
```

クエリと同様に、ミューテーションフィールドは、APIへのエントリーポイントを提供する[ルート操作型](https://spec.graphql.org/draft/#sec-Root-Operation-Types)の1つに追加されます。この場合、`Mutation`型に`createReview`フィールドを定義します。

ミューテーションフィールドは引数も受け入れることができ、`review`引数が`ReviewInput`に設定された入力型を持っていることに気付くかもしれません。これは[入力オブジェクト型](/learn/schema/#input-object-types)として知られており、個々のスカラー値のみではなく、ミューテーションが使用できる情報を含む構造化オブジェクトを渡すことができます。

クエリと同様に、ミューテーションフィールドがオブジェクト型を返す場合、操作でそのフィールドの選択セットを指定する必要があります：

```graphql
# { "graphiql": true, "variables": { "ep": "JEDI", "review": { "stars": 5, "commentary": "This is a great movie!" } } }
mutation CreateReviewForEpisode($ep: Episode!, $review: ReviewInput!) {
  createReview(episode: $ep, review: $review) {
    stars
    commentary
  }
}
```

`createReview`フィールドはスキーマ内の任意の有効な出力型で定義できますが、ミューテーション中に変更されるものに関連する出力型を指定するのが慣例です—この場合、`Review`型です。これは、更新後にオブジェクトの新しい状態を取得する必要があるクライアントにとって有用です。

GraphQLは既存のコードとデータで動作することを意図しているため、レビューの実際の作成は、クライアントがこの操作をGraphQLサーバーに送信したときにあなた次第です。`createReview`ミューテーション中に新しいレビューをデータベースに書き込む仮想的な関数は、次のようになるかもしれません：

```js
const Mutation = {
  createReview(_obj, args, context, _info) {
    return context.db
      .createNewReview(args.episode, args.review)
      .then(reviewData => new Review(reviewData));
  },
};
```

フィールドにデータを提供する方法について詳しくは、[実行ページ](/learn/execution)をご覧ください。

## 既存データの更新

同様に、ミューテーションを使用して既存のデータを更新します。人間の名前を変更するために、新しいミューテーションフィールドを定義し、そのフィールドの出力型を`Human`型に設定して、サーバーがデータを正常に書き込んだ後、更新された人間の情報をクライアントに返すことができるようにします：

```graphql
type Mutation {
  updateHumanName(id: ID!, name: String!): Human
}
```

この操作は、ルーク・スカイウォーカーの名前を更新します：

```graphql
# { "graphiql": true, "variables": { "id": "1000", "name": "Luke Starkiller" } }
mutation UpdateHumanName($id: ID!, $name: String!) { 
  updateHumanName(id: $id, name: $name ) {
    id
    name
  }
}
```

## 目的別のミューテーション

前の例は、RESTとの重要な違いを示しています。REST APIを使用して人間のプロパティを更新する場合、`PATCH`リクエストを使用して、そのリソースの汎用エンドポイントに更新されたデータを送信する可能性があります。GraphQLでは、単に`updateHuman`ミューテーションを作成するのではなく、`updateHumanName`のような、手元のタスクのために設計されたより具体的なミューテーションフィールドを定義できます。

目的別のミューテーションフィールドは、フィールド引数の入力型を非null型にできるようにすることで、スキーマをより表現力豊かにするのに役立ちます（汎用の`updateHuman`ミューテーションは、異なる更新シナリオを処理するために多くのnull許容引数を受け入れる必要がある可能性があります）。スキーマでこの要件を定義することで、クライアントの望む書き込み操作を実行するために適切な値が送信されたことを判断するための他のランタイムロジックの必要性も排除されます。

GraphQLはまた、基本的なCRUDスタイルのリクエストでは意味的にモデル化するのがより困難なデータ間の関係を表現することを可能にします。例えば、ユーザーが映画の個人的な評価を保存したい場合があります。評価はユーザーに属し、映画自体に関連するものを変更しませんが、次のように`Film`オブジェクトに人間工学的に関連付けることができます：

```graphql
# { "graphiql": true, "variables": { "episode": "EMPIRE", "rating": "THUMBS_UP" } }
mutation RateFilm($episode: Episode!, $rating: FilmRating!) { 
  rateFilm(episode: $episode, rating: $rating) {
    episode
    viewerRating
  }
}
```

一般的なルールとして、GraphQL APIは、クライアントにとって意味のある方法でデータを取得および変更するのに役立つように設計されるべきであるため、スキーマで定義されるフィールドは、それらのユースケースに基づいて決定されるべきです。

## 既存データの削除

REST APIでリソースを削除するために`DELETE`リクエストを送信できるのと同様に、`Mutation`型に別のフィールドを定義することで、ミューテーションを使用して既存のデータを削除することもできます：

```graphql
type Mutation {
  deleteStarship(id: ID!): ID!
}
```

新しいミューテーションフィールドの例を次に示します：

```graphql
# { "graphiql": true, "variables": { "id": "3003" } }
mutation DeleteStarship($id: ID!) { 
  deleteStarship(id: $id)
}
```

データを作成および更新するミューテーションと同様に、GraphQL仕様は、データを削除する成功したミューテーション操作から何を返すべきかを示していませんが、スキーマ内のフィールドの出力型として何らかの型を指定する必要があります。一般的に、削除されたエンティティのIDまたはエンティティに関するデータを含むペイロードオブジェクトが、操作が成功したことを示すために使用されます。

## ミューテーション内の複数のフィールド

ミューテーションは、クエリと同様に、複数のフィールドを含むことができます。名前以外に、クエリとミューテーションの間には1つの重要な違いがあります：

**クエリフィールドは並行して実行されますが、ミューテーションフィールドは順次実行されます。**

例を見てみましょう：

```graphql
# { "graphiql": true }
mutation { 
  firstShip: deleteStarship(id: "3001")
  secondShip: deleteStarship(id: "3002")
}
```

これらの最上位フィールドの[順次実行](https://spec.graphql.org/draft/#sec-Normal-and-Serial-Execution)は、1つのリクエストで2つの`deleteStarship`ミューテーションを送信する場合、最初のミューテーションが2番目のミューテーションが開始する前に完了することが保証されることを意味し、自分自身との競合状態に陥らないようにします。

最上位の`Mutation`フィールドの順次実行は、データベーストランザクションの概念とは異なることに注意してください。一部のミューテーションフィールドは正常に解決される場合がありますが、他のフィールドはエラーを返す場合があり、これが発生したときにGraphQLが操作の成功した部分を元に戻す方法はありません。したがって、前の例では、最初の宇宙船が正常に削除されたが、`secondShip`フィールドがエラーを発生させた場合、GraphQLがその後`firstShip`フィールドの実行を元に戻すための組み込み方法はありません。

## 次のステップ

ミューテーションについて学んだことをまとめると：

- クライアントは、スキーマで公開されている機能に応じて、GraphQL APIを使用してデータを作成、更新、および削除できます
- クライアントの要件に応じて、ミューテーションは書き込み操作の細かいユースケースに対応するように設計できます
- `Mutation`型の最上位フィールドは、他の型のフィールドとは異なり、並行して実行されることが多いのに対し、順次実行されます

GraphQLサーバーを使用してデータを読み書きする方法がわかったので、[サブスクリプション](/learn/subscriptions)を使用してリアルタイムでデータを取得する方法を学ぶ準備ができました。GraphQLクエリとミューテーションを[HTTP経由で提供する](/learn/serving-over-http/)方法についても詳しく学ぶことをお勧めします。
