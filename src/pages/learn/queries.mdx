# クエリ

<p className="learn-subtitle">GraphQLサーバーからデータを取得する方法を学ぶ</p>

GraphQLは3つの主要な操作タイプ（クエリ、ミューテーション、サブスクリプション）をサポートしています。このガイドではすでに基本的なクエリの例をいくつか見てきましたが、このページでは、クエリ操作のさまざまな機能を使用してサーバーからデータを読み取る方法について詳しく学びます。

## フィールド

最もシンプルに言えば、GraphQLはオブジェクトに対して特定の[フィールド](https://spec.graphql.org/draft/#sec-Language.Fields)を要求することです。スキーマの`Query`型に定義されている`hero`フィールドを見ることから始めましょう：

```graphql
type Query {
  hero: Character
}
```

クエリを実行すると、どのような結果が得られるか見てみましょう：

```graphql
# { "graphiql": true }
{
  hero {
    name
  }
}
```

GraphQLの_ドキュメント_を作成する際は、常に[ルート操作タイプ](/learn/schema/#the-query-mutation-and-subscription-types)（この例では`Query`オブジェクト型）から始めます。これはAPIのエントリーポイントとして機能するためです。そこから、興味のあるフィールドの_セレクションセット_を指定し、ScalarまたはEnum型であるリーフ値まで指定する必要があります。`name`フィールドは`String`型を返します。この場合、スター・ウォーズの主人公の名前である`"R2-D2"`です。

GraphQL仕様では、リクエストの結果はレスポンスのトップレベルの`data`キーで返されることが示されています。リクエストでエラーが発生した場合、トップレベルの`errors`キーに何が間違っていたかについての情報が含まれます。そこから、結果がクエリと同じ形状を持っていることがわかります。これはGraphQLにとって不可欠です。なぜなら、常に期待通りのものが返され、サーバーはクライアントが要求しているフィールドを正確に把握しているからです。

前の例では、ヒーローの名前を要求しただけで、`String`が返されましたが、フィールドはオブジェクト型（およびそのリスト）を返すこともできます。その場合、そのオブジェクト型のフィールドの_サブセレクション_を行うことができます：

```graphql
# { "graphiql": true }
{
  hero {
    name
    friends {
      name
    }
  }
}
```

GraphQLクエリは関連するオブジェクトとそのフィールドをトラバースでき、クライアントは古典的なRESTアーキテクチャで必要とされる複数の往復を行う代わりに、1回のリクエストで多くの関連データを取得できます。

この例では、`friends`フィールドがアイテムの配列を返すことに注意してください。GraphQLクエリは、単一のアイテムでもアイテムのリストでも同じように見えます。ただし、スキーマに示されているものに基づいて、どちらを期待するかがわかります。

## 引数

オブジェクトとそのフィールドをトラバースすることしかできなかったとしても、GraphQLはすでにデータ取得にとって非常に便利な言語でしょう。しかし、フィールドに[引数](https://spec.graphql.org/draft/#sec-Language.Arguments)を渡す機能を追加すると、はるかに興味深いものになります：

```graphql
type Query {
  human(id: ID!): Human
}
```

クライアントは、クエリと共に必要な`id`値を提供する必要があります：

```graphql
# { "graphiql": true }
{
  human(id: "1000") {
    name
    height
  }
}
```

RESTのようなシステムでは、単一の引数セット（リクエスト内のクエリパラメータとURLセグメント）のみを渡すことができます。しかしGraphQLでは、すべてのフィールドとネストされたオブジェクトが独自の引数セットを持つことができ、GraphQLは複数のAPI取得を完全に置き換えるものになります。

Scalar型を出力するフィールドに引数を渡すこともできます。この使用例の1つは、すべてのクライアントで個別に行うのではなく、サーバー側で一度データ変換を実装することです：

```graphql
# { "graphiql": true }
{
  human(id: "1000") {
    name
    height(unit: FOOT)
  }
}
```

引数は多くの異なる型を持つことができます。上記の例では、有限のオプションセットの1つを表すEnum型を使用しています（この場合、長さの単位、`METER`または`FOOT`のいずれか）。GraphQLには[デフォルトの型セット](/learn/schema/#scalar-types)が付属していますが、GraphQLサーバーは、トランスポート形式にシリアライズできる限り、カスタム型を宣言することもできます。

[GraphQL型システムの詳細については、こちらをご覧ください。](/learn/schema)

## 操作タイプと名前

上記の例では、操作のセレクションセットの前に`query`キーワードを省略する省略構文を使用してきました。_操作タイプ_を明示的に指定することに加えて、一意の_操作名_を追加することもできます。これは本番アプリで便利です。なぜなら、デバッグとトレースが容易になるからです。

次は、操作タイプとして`query`キーワード、操作名として`HeroNameAndFriends`を含む例です：

```graphql
# { "graphiql": true }
query HeroNameAndFriends {
  hero {
    name
    friends {
      name
    }
  }
}
```

操作タイプは`query`、`mutation`、または`subscription`のいずれかで、実行しようとしている操作のタイプを記述します。このキーワードは、クエリの省略構文を使用している場合を除いて必須です（ミューテーションとサブスクリプションでは常に必須です）。さらに、操作に名前を付けたい場合は、操作タイプも指定する必要があります。

操作名は、操作に割り当てる明示的な名前です。意味のある名前を選択する必要があります。1つのドキュメントで複数の操作を送信する場合は必須ですが、1つの操作のみを送信する場合でも、操作名はデバッグとサーバーサイドのログ記録に役立つため、推奨されます。何か問題が発生した場合（ネットワークログまたはGraphQLサーバーのログにエラーが表示される場合）、内容を解読しようとするのではなく、名前でコードベース内のクエリを識別する方が簡単です。

お気に入りのプログラミング言語の関数名のようなものと考えてください。たとえば、JavaScriptでは、無名関数のみで簡単に作業できますが、関数に名前を付けると、追跡、コードのデバッグ、呼び出されたときのログ記録が容易になります。同様に、GraphQLのクエリとミューテーションの名前、およびフラグメント名は、サーバー側で異なるGraphQLリクエストを識別するための便利なデバッグツールになります。

## エイリアス

鋭い目をお持ちの方は、結果オブジェクトフィールドがクエリ内のフィールドの名前と一致するが引数を含まないため、異なる引数で同じフィールドを直接クエリできないことに気付いたかもしれません。そのため、[エイリアス](https://spec.graphql.org/draft/#sec-Field-Alias)が必要です。これにより、フィールドの結果を任意の名前に変更できます。

```graphql
# { "graphiql": true }
query {
  empireHero: hero(episode: EMPIRE) {
    name
  }
  jediHero: hero(episode: JEDI) {
    name
  }
}
```

上記の例では、2つの`hero`フィールドが衝突しますが、異なる名前にエイリアスできるため、1つのリクエストで両方の結果を取得できます。

## 変数

これまで、すべての引数をクエリ文字列内に記述してきました。しかし、ほとんどのアプリケーションでは、フィールドへの引数は動的になります。たとえば、興味のあるスター・ウォーズのエピソードを選択できるドロップダウン、検索フィールド、またはフィルタのセットがある場合があります。

これらの動的引数をクエリ文字列に直接渡すのは良い考えではありません。なぜなら、クライアント側のコードが実行時にクエリ文字列を動的に操作し、GraphQL固有の形式にシリアライズする必要があるからです。代わりに、GraphQLには、動的値をクエリから切り出し、別の辞書として渡すファーストクラスの方法があります。これらの値は[変数](https://spec.graphql.org/draft/#sec-Language.Variables)と呼ばれます。

変数を使い始めると、次の3つのことを行う必要があります：

1. クエリ内の静的値を`$variableName`に置き換えます
2. `$variableName`をクエリが受け入れる変数の1つとして宣言します
3. トランスポート固有の（通常はJSON）変数辞書で`variableName: value`を渡します

すべてをまとめると、次のようになります：

```graphql
# { "graphiql": true, "variables": { "episode": "JEDI" } }
query HeroNameAndFriends($episode: Episode) {
  hero(episode: $episode) {
    name
    friends {
      name
    }
  }
}
```

<Callout type="info">
変数を使用するには、GraphQLドキュメントで操作タイプと名前を指定する必要があります。
</Callout>

これで、クライアントコードで、完全に新しいクエリを構築する必要なく、単に異なる変数を渡すことができます。一般的に、これはクエリ内でどの引数が動的であると予想されるかを示すための良い方法でもあります。ユーザー提供の値からクエリを構築するために文字列補間を行うべきではありません。

### 変数定義

変数定義は、上記のクエリの`($episode: Episode)`のような部分です。これは、型付き言語の関数の引数定義と同じように機能します。すべての変数を`$`で始まり、その後に型が続くリストとして列挙します。この場合は`Episode`です。

宣言されたすべての変数は、Scalar、Enum、またはInput Object型である必要があります。したがって、複雑なオブジェクトをフィールドに渡したい場合は、サーバー上でそれに一致する[入力型](/learn/schema/#input-object-types)を知っておく必要があります。

変数定義はオプションまたは必須にできます。上記の例では、`Episode`型の横に`!`がないため、オプションです。ただし、変数を渡すフィールドがnull非許容の引数を必要とする場合は、変数も必須である必要があります。

これらの変数定義の構文について詳しく学ぶには、スキーマ定義言語（SDL）を学ぶと便利です。これは[スキーマと型のページ](/learn/schema)で詳しく説明されています。

### デフォルト変数

型宣言の後にデフォルト値を追加することで、クエリ内の変数にデフォルト値を割り当てることもできます：

```graphql
query HeroNameAndFriends($episode: Episode = JEDI) {
  hero(episode: $episode) {
    name
    friends {
      name
    }
  }
}
```

すべての変数にデフォルト値が提供されている場合、変数を渡さずにクエリを呼び出すことができます。変数辞書の一部として変数が渡された場合、それらはデフォルト値を上書きします。

## フラグメント

アプリに比較的複雑なページがあり、2人のヒーローとその友達を並べて見ることができるとしましょう。このようなクエリは、比較の各側に対してフィールドを少なくとも1回繰り返す必要があるため、すぐに複雑になる可能性があることが想像できます。

そのため、GraphQLには[フラグメント](https://spec.graphql.org/draft/#sec-Language.Fragments)と呼ばれる再利用可能な単位が含まれています。フラグメントを使用すると、フィールドのセットを構築し、必要に応じてクエリに含めることができます。フラグメントを使用して上記の状況を解決する方法の例を次に示します：

```graphql
# { "graphiql": true }
query {
  leftComparison: hero(episode: EMPIRE) {
    ...comparisonFields
  }
  rightComparison: hero(episode: JEDI) {
    ...comparisonFields
  }
}

fragment comparisonFields on Character {
  name
  appearsIn
  friends {
    name
  }
}
```

フラグメントを使用できなかった場合、上記のクエリがどれほど繰り返しが多くなるかがわかります。フラグメントの概念は、複雑なアプリケーションのデータ要件をより小さなチャンクに分割するために頻繁に使用されます。特に、多くのUIコンポーネントを異なるフラグメントと組み合わせて1つの初期データ取得にする必要がある場合に便利です。

### フラグメント内での変数の使用

フラグメントは、操作で宣言された変数にアクセスすることもできます：

```graphql
# { "graphiql": true }
query HeroComparison($first: Int = 3) {
  leftComparison: hero(episode: EMPIRE) {
    ...comparisonFields
  }
  rightComparison: hero(episode: JEDI) {
    ...comparisonFields
  }
}

fragment comparisonFields on Character {
  name
  friendsConnection(first: $first) {
    totalCount
    edges {
      node {
        name
      }
    }
  }
}
```

### インラインフラグメント

他の多くの型システムと同様に、GraphQLスキーマにはInterfaceとUnion型を定義する機能が含まれています。詳細については、[スキーマと型のページ](/learn/schema/#interfaces)をご覧ください。

InterfaceまたはUnion型を返すフィールドをクエリする場合、基になる具象型のデータにアクセスするために_インラインフラグメント_を使用する必要があります。例を見るのが最も簡単です：

```graphql
# { "graphiql": true, "variables": { "ep": "JEDI" } }
query HeroForEpisode($ep: Episode!) {
  hero(episode: $ep) {
    name
    ... on Droid {
      primaryFunction
    }
    ... on Human {
      height
    }
  }
}
```

このクエリでは、`hero`フィールドは`Character`型を返しますが、これは`episode`引数に応じて`Human`または`Droid`のいずれかになる可能性があります。直接選択では、`name`のような`Character`インターフェース上のフィールドのみを要求できます。

具象型のフィールドを要求するには、型条件を持つインラインフラグメントを使用する必要があります。最初のフラグメントは`... on Droid`としてラベル付けされているため、`primaryFunction`フィールドは、`hero`から返された`Character`が`Droid`型の場合にのみ実行されます。`Human`型の`height`フィールドについても同様です。

名前付きフラグメントは常に型が付随しているため、同じ方法で使用することもできます。

### メタフィールド

[Union型](/learn/schema/#union-types)で見たように、GraphQLサービスからどの型が返されるかわからない状況があるため、クライアント上でそのデータをどのように処理するかを決定する方法が必要です。

GraphQLでは、クエリ内の任意の時点で`__typename`というメタフィールドを要求して、その時点でのオブジェクト型の名前を取得できます：

```graphql
# { "graphiql": true}
{
  search(text: "an") {
    __typename
    ... on Human {
      name
    }
    ... on Droid {
      name
    }
    ... on Starship {
      name
    }
  }
}
```

上記のクエリでは、`search`は3つのオプションのいずれかとなるUnion型を返します。`__typename`フィールドがなければ、クライアントが異なる型を区別することは不可能です。

2つのアンダースコア（`__`）で始まるすべてのフィールド名は、GraphQLによって予約されています。`__typename`に加えて、GraphQLサービスは[イントロスペクション](/learn/introspection)システムを公開する`__schema`および`__type`メタフィールドを提供します。

## ディレクティブ

前述したように、変数を使用することで、動的クエリを構築するための手動の文字列補間を回避できます。引数で変数を渡すことで、これらの問題の大部分が解決されますが、変数を使用してクエリの構造と形状を動的に変更する方法も必要になる場合があります。たとえば、要約ビューと詳細ビューを持つUIコンポーネントがあり、一方が他方よりも多くのフィールドを含む場合を想像できます。

このようなコンポーネントのクエリを構築してみましょう：

```graphql
# { "graphiql": true, "variables": { "episode": "JEDI", "withFriends": false } }
query Hero($episode: Episode, $withFriends: Boolean!) {
  hero(episode: $episode) {
    name
    friends @include(if: $withFriends) {
      name
    }
  }
}
```

上記の変数を編集して、`withFriends`に`true`を渡すと、結果がどのように変わるか試してみてください。

GraphQLの[ディレクティブ](https://spec.graphql.org/draft/#sec-Type-System.Directives)と呼ばれる機能を使用する必要がありました。具体的には、_実行可能ディレクティブ_は、クライアントによってフィールドまたはフラグメントの包含に添付でき、サーバーが望む方法でクエリの実行に影響を与えることができます。コアGraphQL仕様には、仕様準拠のGraphQLサーバー実装でサポートする必要がある2つのディレクティブが含まれています：

- `@include(if: Boolean)` 引数が`true`の場合のみ、このフィールドを結果に含めます。
- `@skip(if: Boolean)` 引数が`true`の場合、このフィールドをスキップします。

ディレクティブは、クエリ内のフィールドを追加および削除するために文字列操作を行う必要がある状況から抜け出すのに役立ちます。サーバー実装は、まったく新しいディレクティブを定義することで、実験的な機能を追加することもできます。

<Callout type="info">
GraphQLスキーマの型、フィールド、または引数に注釈を付けるために使用できるディレクティブを定義する方法に関する情報をお探しですか？型システムディレクティブの定義と使用の詳細については、[スキーマと型のページ](/learn/schema/#directives)をご覧ください。
</Callout>

## 次のステップ

クエリについて学んだことをまとめましょう：

- データを読み取るGraphQL操作は、`query`ルート操作タイプから始まり、セレクションセット内のフィールドをScalarまたはEnum型のリーフ値までトラバースします
- フィールドは、そのフィールドの出力を変更する引数を受け入れることができます
- 操作は、その型を示すために`query`、`mutation`、または`subscription`キーワードを使用できます
- 操作タイプキーワードは、特定のクエリ操作でのみ省略できます
- 操作には一意の名前を付ける必要があります。これにより、リクエストがより表現力豊かになり、デバッグに役立ちます
- フィールドエイリアスを使用すると、レスポンスキーの名前を変更したり、同じクエリで同じフィールドを複数回含めたり、エイリアスされたフィールドに異なる引数を提供したりできます
- 変数は`$`文字で始まり、フィールド引数に動的な値を提供するために使用できます
- フラグメントは、複数のクエリで必要に応じて使用できる再利用可能なフィールドのセレクションセットです
- 実行可能ディレクティブをクエリに適用して、サーバー上で実行されるときにGraphQLクエリの結果を変更できます
- すべての仕様準拠GraphQLサーバーには、`@include`および`@skip`組み込みディレクティブが含まれています

これで、クエリ操作を使用してGraphQLサーバーからデータを読み取る方法のすべてを理解したので、[ミューテーション](/learn/mutations/)を使用してデータを変更し、副作用をトリガーする方法を学びましょう。
