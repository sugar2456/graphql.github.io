# HTTP経由での提供

<p className="learn-subtitle">HTTPサーバーを使用してGraphQLリクエストに応答する</p>

GraphQL仕様は、APIリクエストとレスポンスを送信する際に特定のクライアント-サーバープロトコルを要求していませんが、HTTPはその普及により最も一般的な選択肢です。このページでは、GraphQLサーバーをHTTP経由で動作するように設定する際に従うべき主要なガイドラインを確認します。

以下のガイドラインは、ステートレスなクエリとミューテーション操作にのみ適用されることに注意してください。これらのリクエストを一般的にサポートするトランスポートプロトコルの詳細については、[サブスクリプションページ](/learn/subscriptions)をご覧ください。

<Callout type="info">
このページの推奨事項は、現在開発中の詳細な[GraphQL-over-HTTP仕様](https://graphql.github.io/graphql-over-http/draft/)と一致しています。まだ最終化されていませんが、このドラフト仕様は、GraphQLクライアントとライブラリのメンテナーにとって単一の情報源として機能し、HTTPトランスポートを使用してGraphQL APIを公開および消費する方法を詳しく説明しています。言語仕様とは異なり、準拠は必須ではありませんが、ほとんどの実装は相互運用性を最大化するためにこれらの標準に向かって進んでいます。
</Callout>

## APIエンドポイント

HTTPは一般的にRESTと関連付けられており、RESTは「リソース」をその核心概念として使用しています。対照的に、GraphQLの概念モデルは[エンティティグラフ](/learn/thinking-in-graphs/)です。その結果、GraphQLのエンティティはURLによって識別されません。代わりに、GraphQLサーバーは単一のURL/エンドポイント（通常は`/graphql`）で動作し、特定のサービスのすべてのGraphQLリクエストはこのエンドポイントに送信される必要があります。

## 認証が行われる場所

ほとんどのモダンなWebフレームワークは、リクエストが_ミドルウェア_のスタック（_フィルター_または_プラグイン_とも呼ばれる）を通過するパイプラインモデルを使用します。リクエストがパイプラインを流れると、検査、変換、変更、またはレスポンスで終了させることができます。GraphQLは、他のHTTPエンドポイントハンドラーと同じセッションとユーザー情報にアクセスできるように、すべての認証ミドルウェアの後に配置する必要があります。

認証後、サーバーはGraphQL実行が開始されるまで、リクエストに関する[認可](/learn/authorization/)決定を行わないでください。具体的には、フィールドレベルの認可は、[GraphQLのExecuteRequest()](https://spec.graphql.org/draft/#ExecuteRequest())中にリゾルバから呼び出されるビジネスロジックによって強制される必要があり、認可関連のエラーが発生した場合に部分的なレスポンスを生成できるようにします。

## リクエスト形式

### ヘッダー

GraphQLクライアントとサーバーは、シリアル化のためにJSONをサポートし、他の形式もサポートする場合があります。クライアントは、`Accept` HTTPヘッダーを使用して、レスポンスでサポートするメディアタイプを示す必要があります。具体的には、クライアントは`Accept`ヘッダーに`application/graphql-response+json`を含める必要があります。

このヘッダーにエンコーディング情報が含まれていない場合、`utf-8`と見なされます。ただし、クライアントがリクエストに`Accept`ヘッダーを提供しない場合、サーバーはエラーで応答する場合があります。

<Callout type="info">
`application/graphql-response+json`は、GraphQL over HTTP仕様のドラフトで説明されています。互換性を確保するために、クライアントが2025年1月1日より前にレガシーGraphQLサーバーにリクエストを送信する場合、`Accept`ヘッダーには次のように`application/json`メディアタイプも含める必要があります：`application/graphql-response+json, application/json`
</Callout>

### メソッド

GraphQL HTTPサーバーは、クエリとミューテーション操作に対してHTTP `POST`メソッドを処理する必要があり、クエリ操作に対して`GET`メソッドも受け入れる場合があります。

#### `POST`リクエストと本文

標準的なGraphQL POSTリクエストは、`Content-type`ヘッダーに`application/json`を設定し、次の形式のJSONエンコードされた本文を含める必要があります：

```json
{
  "query": "...",
  "operationName": "...",
  "variables": { "myVariable": "someValue", ... },
  "extensions": { "myExtension": "someValue", ... }
}
```

`query`パラメータは必須で、GraphQLドキュメントのソーステキストが含まれます。ここでの`query`という用語は誤称であることに注意してください：ドキュメントには任意の有効なGraphQL操作（および関連するフラグメント）が含まれる可能性があります。

`operationName`、`variables`、および`extensions`パラメータはオプションフィールドです。`operationName`は、`query`ドキュメントに複数の操作が存在する場合にのみ必要です。

クライアントのリクエストに`Content-type`ヘッダーが欠落している場合、サーバーは`4xx`ステータスコードで応答する必要があることに注意してください。`Accept`ヘッダーと同様に、この情報が明示的に提供されていない場合、`application/json`メディアタイプのリクエスト本文に対して`utf-8`エンコーディングが想定されます。

#### `GET`リクエストとパラメータ

HTTP GETリクエストを受信する場合、GraphQLドキュメントはクエリ文字列の`query`パラメータで提供される必要があります。例えば、次のGraphQLクエリを実行したい場合：

```graphql
{
  me {
    name
  }
}
```

このリクエストは、次のようにHTTP GET経由で送信できます：

```
http://myapi/graphql?query={me{name}}
```

クエリ変数は、`variables`という追加のクエリパラメータでJSONエンコードされた文字列として送信できます。クエリに複数の名前付き操作が含まれている場合、`operationName`クエリパラメータを使用して、実行する操作を制御できます。

#### HTTPメソッドの選択

GraphQLリクエストのHTTPメソッドを選択する際に、考慮すべき点がいくつかあります。まず、`POST`以外のHTTPメソッドのサポートは、GraphQLサーバーの裁量によるため、クライアントはサポートされている動詞に制限されます。

さらに、`GET` HTTPメソッドは`query`操作にのみ使用できるため、クライアントが`mutation`操作の実行をリクエストする場合、代わりに`POST`メソッドを使用する必要があります。

サーバーがクエリ操作に対して`GET`メソッドをサポートしている場合、クライアントはHTTPキャッシングまたはコンテンツ配信ネットワーク（CDN）でのエッジキャッシングを促進するためにこのオプションを活用することが推奨される場合があります。ただし、GraphQLドキュメント文字列は複雑な操作に対して非常に長くなる可能性があるため、クエリパラメータがブラウザとCDNがURLの長さに課す制限を超える可能性があります。

このような場合、一般的なアプローチは、サーバーが[_persisted documents_](https://github.com/graphql/graphql-over-http/pull/264)、_automatic persisted queries_、または_trusted documents_などの手法を使用して識別されたGraphQLドキュメントを保存することです。これにより、クライアントは完全なクエリテキストの代わりに短いドキュメント識別子を送信できます。

## レスポンス形式

### ヘッダー

レスポンスタイプは`application/graphql-response+json`である必要がありますが、レガシークライアントをサポートするために`application/json`にすることもできます。サーバーは、レスポンスの`Content-type`ヘッダーでメディアタイプを示します。エンコーディングも示す必要があり、そうでない場合は`utf-8`が想定されます。

### 本文

クエリと変数を送信するために使用されるHTTPメソッドに関係なく、レスポンスはJSON形式でリクエストの本文で返される必要があります。GraphQL仕様で述べられているように、クエリは一部のデータといくつかのエラーをもたらす可能性があり、それらは次の形式のJSONオブジェクトで返される必要があります：

```json
{
  "data": { ... },
  "errors": [ ... ],
  "extensions": { ... }
}
```

エラーが返されなかった場合、`errors`フィールドはレスポンスに存在してはなりません。実行が開始される前にエラーが発生した場合、`errors`フィールドにはこれらのエラーが含まれ、`data`フィールドはレスポンスに存在してはなりません。`extensions`フィールドはオプションであり、ここで提供される情報はGraphQL実装の裁量によります。

GraphQL仕様に準拠したレスポンス形式について詳しくは、[レスポンスページ](/learn/response/)をご覧ください。

### ステータスコード

レスポンスに`data`キーが含まれ、その値が`null`でない場合、サーバーは`application/graphql-response+json`または`application/json`メディアタイプのいずれかに対して`2xx`ステータスコードで応答する必要があります。これは、レスポンスにエラーが含まれている場合でも当てはまります。HTTPにはまだ「部分的な成功」を表すステータスコードがないためです。

GraphQL操作の実行を妨げる検証エラーについては、サーバーは通常`400`ステータスコードを送信しますが、一部のレガシーサーバーは`application/json`メディアタイプが使用されている場合に`2xx`ステータスコードを返す場合があります。

`application/json`メディアタイプで応答するレガシーサーバーについては、実行に失敗した有効なGraphQLリクエストに対して`4xx`および`5xx`ステータスコードの使用は推奨されませんが、実装によっては使用される場合があります。サーバー側エラーのソースに関する潜在的な曖昧さのため、このメディアタイプでは代わりに`2xx`コードを使用する必要があります。

ただし、`application/graphql-response+json`メディアタイプのレスポンスについては、有効なGraphQLリクエストが実行に失敗した場合、サーバーは`4xx`または`5xx`ステータスコードで応答します。

## まとめ

HTTP経由でGraphQLを提供するためのこれらの推奨事項をまとめると：

- サーバーは、GraphQLリクエストが検証される前にユーザー認証を処理する必要があります。認可は、GraphQLリクエスト実行中にビジネスロジック内で行われる必要があります
- GraphQL APIは、通常`/graphql`で終わる単一のエンドポイントで公開されます
- GraphQLクライアントとサーバーはJSONをサポートする必要がありますが、他の形式もサポートする場合があります
- クライアントは、`Accept`ヘッダーに`application/graphql-response+json`のメディアタイプを示す必要があります
- GraphQLリクエストは`POST` HTTPメソッドを使用して送信されますが、クエリ操作は`GET`メソッドを使用して送信することもできます
- クライアントは、`POST`リクエストに対して`application/json`の値を持つ`Content-type`ヘッダーも提供する必要があります
- 実行されたGraphQL操作の完全または部分的な結果は、レスポンスのJSONエンコードされた本文の`data`キーで利用可能になり、検証または実行中に発生したエラーに関する情報は`errors`キーで利用可能になります
- 失敗した有効なGraphQL操作のレスポンスステータスコードは、レスポンスの示されたメディアタイプによって異なる場合がありますが、非nullの`data`キーを持つGraphQLレスポンスは`2xx`レスポンスを提供します
