# ページネーション

<p className="learn-subtitle">一貫したフィールドページネーションモデルでオブジェクトのリストをトラバースする</p>

GraphQLでの一般的なユースケースは、オブジェクトのセット間の関係をトラバースすることです。これらの関係をGraphQLで公開する方法はさまざまで、クライアント開発者にさまざまな機能セットを提供します。このページでは、カーソルベースの接続モデルを使用してフィールドをページネーションする方法について説明します。

## 複数形

オブジェクト間の接続を公開する最も簡単な方法は、複数の[リスト型](/learn/schema/#list)を返すフィールドを使用することです。例えば、R2-D2の友達のリストを取得したい場合、それらすべてを要求するだけです：

```graphql
# { "graphiql": true }
query {
  hero {
    name
    friends {
      name
    }
  }
}
```

## スライシング

しかし、すぐに、クライアントが望む追加の動作があることに気づきます。クライアントは、取得したい友達の数を指定できるようにしたいかもしれません—おそらく最初の2人だけを取得したいでしょう。そのため、次のようなものを公開したいと思います：

```graphql
query {
  hero {
    name
    friends(first: 2) {
      name
    }
  }
}
```

しかし、最初の2つだけを取得した場合、リストをページネーションすることもできます。クライアントが最初の2人の友達を取得した後、次の2人の友達を尋ねるために2番目のリクエストを送信したい場合があります。その動作をどのように有効にできるでしょうか？

## ページネーションとエッジ

ページネーションを行う方法はいくつかあります：

- リスト内の次の2つを尋ねるために、`friends(first:2 offset:2)`のようなことを行うことができます。
- 取得した最後の友達の後の次の2つを尋ねるために、`friends(first:2 after:$friendId)`のようなことを行うことができます。
- 最後のアイテムからカーソルを取得し、それを使用してページネーションするために、`friends(first:2 after:$friendCursor)`のようなことを行うことができます。

最初の箇条書きで説明されているアプローチは、古典的な_オフセットベースのページネーション_です。しかし、このスタイルのページネーションは、特に大きなデータセットの場合、パフォーマンスとセキュリティの欠点がある可能性があります。さらに、ユーザーが結果のページをリクエストした後にデータベースに新しいレコードが追加された場合、後続のページのオフセット計算が曖昧になる可能性があります。

一般的に、_カーソルベースのページネーション_が設計されたものの中で最も強力であることがわかりました。特にカーソルが不透明である場合、オフセットベースまたはIDベースのページネーションのいずれも、カーソルベースのページネーションを使用して実装できます（カーソルをオフセットまたはIDにすることで）。カーソルを使用することで、将来ページネーションモデルが変更された場合に追加の柔軟性が得られます。カーソルが不透明であり、その形式に依存すべきではないことを思い出すために、base64エンコードすることをお勧めします。

しかし、それは問題につながります—オブジェクトからカーソルをどのように取得するのでしょうか？カーソルを`User`型に配置したくはありません。それは接続のプロパティであり、オブジェクトのプロパティではありません。そのため、新しい間接層を導入したいかもしれません。`friends`フィールドは、エッジのリストを提供する必要があり、エッジにはカーソルと基盤となるノードの両方があります：

```graphql
query {
  hero {
    name
    friends(first: 2) {
      edges {
        node {
          name
        }
        cursor
      }
    }
  }
}
```

エッジの概念は、オブジェクトの1つではなく、エッジに固有の情報がある場合にも有用であることがわかります。例えば、APIで「友情の時間」を公開したい場合、それをエッジに配置することは自然な場所です。

## リストの終わり、カウント、および接続

これで、カーソルを使用して接続をページネーションできますが、接続の終わりに到達したことをどのように知るのでしょうか？空のリストが返されるまでクエリを続ける必要がありますが、追加のリクエストが不要になるように、接続が終わりに到達したことを伝えてほしいと思います。同様に、接続自体に関する追加情報が必要な場合はどうでしょうか？例えば、R2-D2には合計で何人の友達がいるでしょうか？

これらの両方の問題を解決するために、`friends`フィールドは接続オブジェクトを返すことができます。接続オブジェクトは、エッジのフィールドと、その他の情報（合計数や次のページが存在するかどうかに関する情報など）を持つオブジェクト型になります。そのため、最終的なクエリは次のようになります：

```graphql
query {
  hero {
    name
    friends(first: 2) {
      totalCount
      edges {
        node {
          name
        }
        cursor
      }
      pageInfo {
        endCursor
        hasNextPage
      }
    }
  }
}
```

この`PageInfo`オブジェクトに`endCursor`と`startCursor`を含めることもできることに注意してください。このように、エッジに含まれる追加情報が不要な場合、`pageInfo`からページネーションに必要なカーソルを取得したため、エッジをクエリする必要がまったくありません。これは、接続の使いやすさの向上につながります。`edges`リストを公開するだけでなく、間接層を避けるために、ノードのみの専用リストも公開できます。

## 完全な接続モデル

明らかに、これは複数形を持つだけの元の設計よりも複雑です！しかし、この設計を採用することで、クライアントにいくつかの機能を解き放ちました：

- リストをページネーションする機能。
- `totalCount`や`pageInfo`など、接続自体に関する情報を尋ねる機能。
- `cursor`や`friendshipTime`など、エッジ自体に関する情報を尋ねる機能。
- ユーザーが不透明なカーソルを使用するだけなので、バックエンドがページネーションを実行する方法を変更する機能。

これを実際に見るために、サンプルスキーマには`friendsConnection`という追加のフィールドがあり、これらの概念をすべて公開しています：

```graphql
interface Character {
  id: ID!
  name: String!
  friends: [Character]
  friendsConnection(first: Int, after: ID): FriendsConnection!
  appearsIn: [Episode]!
}

type FriendsConnection {
  totalCount: Int
  edges: [FriendsEdge]
  friends: [Character]
  pageInfo: PageInfo!
}

type FriendsEdge {
  cursor: ID!
  node: Character
}

type PageInfo {
  startCursor: ID
  endCursor: ID
  hasNextPage: Boolean!
}
```

サンプルクエリで試すことができます。`friendsConnection`フィールドの`after`引数を削除して、ページネーションがどのように影響を受けるかを確認してください。また、接続上のヘルパー`friends`フィールドで`edges`フィールドを置き換えてみてください。これにより、クライアントに適切な場合、追加のエッジ間接層なしで直接友達のリストを取得できます：

```graphql
# { "graphiql": true }
query {
  hero {
    name
    friendsConnection(first: 2, after: "Y3Vyc29yMQ==") {
      totalCount
      edges {
        node {
          name
        }
        cursor
      }
      pageInfo {
        endCursor
        hasNextPage
      }
    }
  }
}
```

## 接続仕様

このパターンの一貫した実装を確保するために、Relayプロジェクトには、カーソルベースの接続パターンを使用するGraphQL APIを構築するために従うことができる正式な[仕様](https://relay.dev/graphql/connections.htm)があります—Relayを使用するかどうかに関係なく。

## まとめ

GraphQLスキーマでフィールドをページネーションするためのこれらの推奨事項をまとめると：

- 多くのデータを返す可能性のあるリストフィールドは、ページネーションする必要があります
- カーソルベースのページネーションは、GraphQLスキーマのフィールドに安定したページネーションモデルを提供します
- Relayプロジェクトからのカーソル接続仕様は、GraphQLスキーマのフィールドをページネーションするための一貫したパターンを提供します
