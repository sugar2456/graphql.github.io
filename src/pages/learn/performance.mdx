# パフォーマンス

<p className="learn-subtitle">GraphQLレスポンスの実行と配信を最適化する</p>

一見すると、GraphQLリクエストは、APIが単一のエンドポイント経由で提供され、クライアントが操作に含めるフィールドを事前に知らない可能性があるため、キャッシュが困難に見えるかもしれません。

しかし、実際には、GraphQLは、特定のエンドポイントに対してクライアントが異なるクエリパラメータを指定できるREST APIなど、パラメータ化されたリクエストを可能にする任意のAPIと同じくらいキャッシュ可能です。クライアント側とサーバー側、およびトランスポート層でGraphQLリクエストを最適化する方法は多数あり、異なるGraphQLサーバーとクライアントライブラリには、一般的なキャッシング機能が直接組み込まれていることがよくあります。

このページでは、APIからデータを取得する方法を最適化するために、GraphQLクライアントとサーバーで活用できるいくつかの異なる戦術について説明します。

## クライアント側のキャッシング

GraphQLクライアントが実装できるクライアント側のキャッシング戦略の範囲があり、パフォーマンスだけでなく、ユーザーに一貫性があり応答性の高いインターフェースをレンダリングすることを保証するのにも役立ちます。[クライアント側のキャッシングについて詳しく読む](/learn/caching)。

## クエリの`GET`リクエスト

[GraphQL over HTTP仕様](https://graphql.github.io/graphql-over-http/draft/)に準拠するGraphQL実装は、デフォルトで`POST` HTTPメソッドをサポートしますが、クエリ操作に対して`GET`リクエストもサポートする場合があります。

`GET`を使用すると、このHTTPメソッドで行われたリクエストがデフォルトでキャッシュ可能と見なされるため、クエリのパフォーマンスを向上させることができ、サーバーレスポンスにキャッシュ関連のヘッダーが提供されている場合、HTTPキャッシングまたはコンテンツ配信ネットワーク（CDN）の使用を促進できます。

ただし、ブラウザとCDNはURLにサイズ制限を課すため、複雑な操作に対してURLのクエリ文字列で大きなドキュメントを送信することは不可能な場合があります。_persisted queries_（_trusted documents_または_automatic persisted queries_の形式）を使用すると、クライアントはクエリのハッシュを送信でき、サーバーは操作を検証して実行する前に、サーバー側ストアでハッシュを検索してドキュメントの完全版を検索できます。

プレーンテキストバージョンの代わりにハッシュされたクエリを送信することには、ネットワークリクエストでクライアントが送信するデータ量を削減するという追加の利点があります。

## N+1問題

GraphQLは、サーバー上でクリーンなコードを記述できるように設計されており、すべての型のすべてのフィールドに、その値を解決するための焦点を絞った単一目的の関数があります。しかし、追加の考慮なしでは、素朴なGraphQLサービスは非常に「おしゃべり」になる可能性があり、データベースからデータを繰り返し読み込む可能性があります。

次のクエリを考えてみましょう—ヒーローとその友達のリストを取得するために、フィールドリゾルバが実行されると、キャラクターオブジェクトを取得するために基盤となるデータソースへの1つのリクエスト、友達を取得するための別のリクエスト、そして各人間の友達の宇宙船のリストを読み込むための3つの後続のリクエストがあると想像できます：

```graphql
# { "graphiql": true }
query HeroWithFriends {
  # ヒーローのための1つのリクエスト
  hero {
    name
    # ヒーローのN人の友達のための1つのリクエスト
    friends {
      name
      # N個の宇宙船リクエスト - ヒーローのN人の人間の友達それぞれに対して1つ
      ... on Human {
        starships {
          name
        }
      }
    }
  }
}
```

これはN+1問題として知られており、基盤となるデータソースへの初期リクエスト（ヒーローの友達のため）が、リクエストされたすべてのフィールドのデータを解決するためのN個の後続のリクエスト（友達の宇宙船データのため）につながります。

これは、バックエンドからの複数のデータリクエストを短い期間に収集し、Facebookの[DataLoader](https://github.com/facebook/dataloader)のようなツールを使用して、基盤となるデータベースまたはマイクロサービスへの単一のリクエストでディスパッチするバッチ処理技術によって一般的に解決されます。さらに、特定のGraphQL実装には、操作選択セットを基盤となるデータソースへの最適化されたクエリに変換できる組み込み機能がある場合があります。

## 需要制御

GraphQLスキーマの設計方法に応じて、クライアントが実行中に基盤となるデータソースに過度の負荷をかける非常に複雑な操作をリクエストする可能性があります。これらの種類の操作は、既知のクライアントによって不注意に送信される可能性がありますが、悪意のあるアクターによって送信される可能性もあります。

特定の需要制御メカニズムは、リストフィールドのページネーション、操作の深度と幅の制限、クエリの複雑さの分析など、これらの操作からGraphQL APIを保護するのに役立ちます。[セキュリティページで需要制御について詳しく読む](/learn/security/#demand-control)。

## JSON（GZIP付き）

GraphQLサービスは、GraphQL仕様が[それを要求していない](http://spec.graphql.org/draft/#sec-Serialization-Format)にもかかわらず、通常JSONを使用して応答します。JSONは、より優れたネットワークパフォーマンスを約束するAPI層にとって奇妙な選択のように見えるかもしれませんが、主にテキストであるため、GZIP、deflate、brotliなどのアルゴリズムで非常にうまく圧縮されます。

本番環境のGraphQLサービスがGZIPを有効にし、クライアントに次のヘッダーを送信することを推奨します：

```text
Accept-Encoding: gzip
```

JSONは、クライアントとAPI開発者にとっても非常に馴染みがあり、読み取りとデバッグが容易です。実際、GraphQL構文は部分的にJSON構文に触発されています。

## パフォーマンス監視

時間の経過とともにGraphQL APIを監視することで、特定の操作がAPIのパフォーマンスにどのように影響するかについての洞察を提供し、その健全性を維持するためにどの調整を行うべきかを判断するのに役立ちます。例えば、基盤となるデータソースへの最適化されていないリクエストにより、特定のフィールドの解決に時間がかかる場合があることや、他のフィールドが実行中に定期的にエラーを発生させる場合があることがわかるかもしれません。

可観測性ツールは、APIサービスをインストルメント化して、リクエスト中にメトリクス、トレース、ログを収集できるようにすることで、特定のGraphQL操作の実行においてボトルネックが存在する場所についての洞察を提供できます。例えば、[OpenTelemetry](https://opentelemetry.io/)は、多くの異なる言語でGraphQL APIのインストルメンテーションをサポートするために使用できるベンダーに依存しないツールのスイートを提供します。

## まとめ

GraphQL APIのパフォーマンスを向上させるためのこれらの推奨事項をまとめると：

- GraphQLクエリ操作に`GET`を使用すると、特にハッシュされたクエリドキュメントと組み合わせて使用する場合、HTTPキャッシングとCDNの使用をサポートできます
- 操作の選択セットは異なる種類のオブジェクト間の関係を表現できるため、N+1問題は、基盤となるデータソースへのリクエストをバッチ処理およびキャッシングすることで、フィールド実行中に軽減できます
- フィールドのページネーション、操作の深度と幅の制限、APIリクエストのレート制限は、個々のGraphQL操作がサーバーリソースに過度の負荷をかけることを防ぐのに役立ちます
- GZIPは、サーバーとクライアントがサポートしている場合、GraphQL JSON形式のレスポンスのサイズを圧縮するために使用できます
- OpenTelemetryなどのパフォーマンス監視ツールを使用して、リクエスト実行に関連するメトリクス、ログ、トレースを収集することで、時間の経過とともにGraphQL APIの全体的な健全性を維持できます
