# 検証

<p className="learn-subtitle">GraphQLがスキーマを使用して操作を検証する方法を学ぶ</p>

このページでは、GraphQLリクエストのライフサイクルにおける重要なフェーズである[検証](https://spec.graphql.org/draft/#sec-Validation)について説明します。リクエストは実行するために構文的に正しい必要がありますが、APIのスキーマに対してチェックされたときに有効である必要もあります。

実際には、GraphQL操作がサーバーに到達すると、ドキュメントはまず解析され、次に型システムを使用して検証されます。これにより、サーバーとクライアントは、ランタイムチェックに依存せずに、無効なクエリが作成されたときに開発者に効果的に通知できます。操作が検証されると、サーバー上で[実行](/learn/execution/)され、レスポンスがクライアントに配信されます。

## 検証の例

GraphQL仕様は、リクエストが有効と見なされるために満たす必要がある詳細な条件を説明しています。以下のセクションでは、GraphQL操作で発生する可能性のある一般的な検証問題のいくつかの例を見ていきます。

### 存在しないフィールドのリクエスト

フィールドをクエリする場合、そのフィールドは関連する型で定義されている必要があります。`hero`は`Character`型を返すため、その選択セットは`Character`型のフィールドのみをリクエストできます。`Character`には`favoriteSpaceship`フィールドがないため、このクエリは無効です：

```graphql
# { "graphiql": true }
# 無効: favoriteSpaceshipはCharacterに存在しません
query {
  hero {
    favoriteSpaceship
  }
}
```

### 選択セットとリーフフィールド

フィールドをクエリし、それがスカラー型または列挙型以外のものを返す場合、フィールドから取得したいデータ（「選択セット」）を指定する必要があります。`hero`クエリフィールドは`Character`を返し、すでにその上で`name`や`appearsIn`のようなフィールドをリクエストする例を見てきました。これらのリーフフィールドの選択を省略すると、クエリは有効ではありません：

```graphql
# { "graphiql": true }
# 無効: heroはスカラーではないため、フィールドが必要です
query {
  hero
}
```

同様に、スカラーまたは列挙型のフィールドをクエリすることは意味がないため、リーフフィールドに選択セットを追加すると、クエリは無効になります：

```graphql
# { "graphiql": true }
# 無効: nameはスカラーであるため、フィールドは許可されません
query {
  hero {
    name {
      firstCharacterOfName
    }
  }
}
```

### 抽象型を出力するフィールドのフラグメントの欠如

以前、クエリは問題の型のフィールドのみを要求できることが指摘されました。したがって、`Character`を返す`hero`をクエリする場合、`Character`インターフェース型に存在するフィールドのみをリクエストできます。しかし、R2-D2の主要機能をクエリしたい場合はどうなるでしょうか？

```graphql
# { "graphiql": true }
# 無効: primaryFunctionはCharacterに存在しません
query {
  hero {
    name
    primaryFunction
  }
}
```

そのクエリは無効です。なぜなら、`primaryFunction`は`Character`インターフェース型によって定義された共有フィールドの1つではないためです。`Character`が`Droid`である場合に`primaryFunction`を取得したいことを示す方法が必要です。それ以外の場合は、そのフィールドを無視します。[フラグメント](/learn/queries/#fragments)を使用してこれを行うことができます。`Droid`で定義されたフラグメントを設定し、それを選択セットに含めることで、定義されている場所でのみ`primaryFunction`をクエリすることを保証します：

```graphql
# { "graphiql": true }
query {
  hero {
    name
    ...DroidFields
  }
}

fragment DroidFields on Droid {
  primaryFunction
}
```

このクエリは有効ですが、少し冗長です。名前付きフラグメントは、複数回使用した場合に価値がありましたが、これは1回しか使用していません。名前付きフラグメントを使用する代わりに、[インラインフラグメント](/learn/queries/#inline-fragments)を使用できます。これにより、別のフラグメントに名前を付けることなく、クエリしている型を示すことができます：

```graphql
# { "graphiql": true }
query {
  hero {
    name
    ... on Droid {
      primaryFunction
    }
  }
}
```

### 循環フラグメント展開

まず、複雑な有効なクエリを見てみましょう。これはネストされたクエリですが、重複したフィールドがフラグメントに因数分解されています：

```graphql
# { "graphiql": true }
query {
  hero {
    ...NameAndAppearances
    friends {
      ...NameAndAppearances
      friends {
        ...NameAndAppearances
      }
    }
  }
}

fragment NameAndAppearances on Character {
  name
  appearsIn
}
```

以下は、上記のクエリの代替案で、明示的な3レベルのネストの代わりに再帰を使用しようとしています。この新しいクエリは無効です。なぜなら、フラグメントは（直接的または間接的に）それ自体を参照できないためです。結果として生じるサイクルは無制限の結果を作成する可能性があるためです！

```graphql
# { "graphiql": true }
query {
  hero {
    ...NameAndAppearancesAndFriends
  }
}

fragment NameAndAppearancesAndFriends on Character {
  name
  appearsIn
  friends {
    ...NameAndAppearancesAndFriends
  }
}
```

これは検証システムの表面をかすめただけです。GraphQL操作が意味的に意味があることを保証するために、多くの検証ルールが存在します。仕様では、[検証セクション](https://spec.graphql.org/draft/#sec-Validation)でこのトピックについて詳しく説明しており、[リファレンス実装の検証ディレクトリ](https://github.com/graphql/graphql-js/blob/main/src/validation)には、仕様に準拠したGraphQLバリデーターを実装するコードが含まれています。

## 検証エラー

上記の例で見たように、GraphQLサーバーがリクエストで検証エラーに遭遇すると、レスポンスの`errors`キーに何が起こったかについての情報を返します。具体的には、GraphQLがドキュメントで検証問題を検出すると、実行が開始される前に_リクエストエラー_を発生させます。これは、部分的なデータがレスポンスに含まれないことを意味します。

また、GraphQL仕様では、すべての実装がスキーマに対して受信リクエストを検証する必要があるため、開発者はこれらの検証問題を手動で処理するための特定のランタイムロジックを記述する必要はありません。

## 次のステップ

検証について学んだことをまとめると：

- 実行されるためには、リクエストに構文的に正しいドキュメントが含まれ、スキーマに対してチェックされたときに有効と見なされる必要があります
- 仕様では、実装が受信リクエストに有効なフィールド選択、正しいフラグメントの使用などが含まれていることを確認する必要があります
- 検証問題が発生した場合、サーバーはリクエストエラーを発生させ、クライアントに何が起こったかについての情報を返します。フィールドの実行は開始されません

検証ステップが正常に完了した後、GraphQLがリクエスト内の各フィールドにデータを提供する方法については、[実行](/learn/execution/)ページに進んでください。
