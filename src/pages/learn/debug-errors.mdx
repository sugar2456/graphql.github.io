# 一般的なHTTPエラーとそのデバッグ方法

HTTP経由でGraphQL APIを構築または消費する際、エラーに遭遇することは一般的です。特に開発中はそうです。これらの問題を認識して解決する方法を理解することで、時間とフラストレーションを節約できます。

このガイドでは、一般的なHTTPエラーとGraphQLエラー、それらの意味、およびそれらを効果的にデバッグする方法について説明します。これは、リクエスト形式、ステータスコード、メディアタイプを含む、GraphQLがHTTP経由でどのように機能するかを標準化する[GraphQL over HTTP仕様（ドラフト）](https://graphql.github.io/graphql-over-http/draft/)の推奨事項に従っています。実装は異なる場合があることに注意してください。そのため、これを決定的なリファレンスではなく、一般的なガイドとして扱ってください。

## `400 Bad Request`: 構文または解析エラー

### 意味

サーバーがリクエストを解析できませんでした。GraphQLクエリ文字列が不正であるか、JSON本文が有効ではありません。これは、GraphQL over HTTP仕様で推奨される主要なエラーステータスです。

### 一般的な原因

- JSON構文エラー
- `{ "query": "..." }`でラップせずにプレーン文字列を送信する
- サポートされていない`Content-Type: application/graphql`を使用する

### デバッグ方法

- リンターまたはフォーマッターを使用してJSON本文を検証します。
- `Content-Type: application/json`ヘッダーで`POST`リクエストを送信していることを確認します。
- GraphQLクエリの構文エラーを確認します。IDEまたはリンターを使用して検証します。

## `405 Method Not Allowed`: 間違ったHTTPメソッド

### 意味

サポートされていないHTTPメソッドを使用しています。ほとんどのGraphQLサーバーは、ミューテーションに`POST`を要求し、クエリに`GET`を許可する場合があります。

### 一般的な原因

- `POST`または`GET`の代わりに`PUT`または`DELETE`リクエストを送信する
- ミューテーションに対して`GET`リクエストを送信する、または`POST`リクエストのみをサポートするサーバーに送信する

### デバッグ方法

- HTTPメソッドを確認します。ミューテーションは`POST`を使用する必要があります。
- サーバーがクエリに対して`GET`をサポートしていることを確認します。
- メソッドのサポートを確認するために[GraphQL over HTTP仕様](https://graphql.github.io/graphql-over-http/draft/)を参照してください。

## `500 Internal Server Error`: 予期しないサーバー障害

### 意味

サーバーで何かが間違っています。

### 一般的な原因

- リゾルバでの未処理の例外
- サーバー起動時のスキーマ検証の問題
- 欠落または誤設定されたミドルウェア

### デバッグ方法

- サーバーログまたはスタックトレースを確認します。
- リゾルバにエラーハンドリングを追加します。

## `200 OK`のGraphQLエラー

### 意味

HTTP層は成功しましたが、GraphQL操作でエラーが発生しました。

### 一般的な原因

- 実行中のランタイムエラー
- スキーマ制約の違反（例：間違ったデータ型を返す、または非null許容位置で`null`を返す）

古いサーバーとクライアント（`Content-Type: application/graphql-response+json`を使用していないもの）は、完全なリクエスト失敗（`data`なし）の場合にも200 OKを使用する場合があります。一般的な原因には以下が含まれます：

- 存在しないフィールドをクエリする
- フィールドに間違った引数を渡す
- 非リーフフィールドで選択セットを省略する
- リクエストに複数の操作が存在する場合に`operationName`を指定しない

### デバッグ方法

レスポンス本文の`errors`配列を確認します。レスポンスに`data`プロパティが含まれている場合、クエリドキュメントはおそらく有効であり、ランタイム例外に遭遇した可能性が高いです—無効な入力、アクセス拒否、またはサーバーロジックのバグが原因である可能性があります。

`data`フィールドがない場合、リクエストは検証中に失敗した可能性があります。例えば：

```json
{
  "errors": [
    {
      "message": "Cannot query field \"foo\" on type \"Query\".",
      "locations": [{ "line": 1, "column": 3 }]
    }
  ]
}
```

イントロスペクションまたはIDEを使用して、クエリがスキーマと一致することを確認します。

## 実装固有のステータスコード

一部のGraphQLサーバー実装は、仕様で明示的に推奨されていない追加のHTTPステータスコードを使用する場合があります。これらは実装によって異なります。

- `415 Unsupported Media Type`: サーバーがリクエストの`Content-Type`を理解できません。これは、GraphQLクエリが`Content-Type: text/plain`または別のサポートされていないタイプで送信された場合に発生する可能性があります。
- `422 Unprocessable Entity`: 一部の実装は、`200` + エラー配列の代わりに、GraphQL検証エラーに対してこれを使用します。

これらのエラーコードは、ほとんどの場合、仕様で推奨されていません。異なるGraphQLサーバーは、検証エラーを異なる方法で処理します。疑問がある場合は、仕様でサポートされているエラーコードを使用してください。

## GraphQLレスポンス形式の理解

従来、GraphQLサーバーは`application/json`メディアタイプを使用してレスポンスを返してきました。しかし、[GraphQL over HTTP仕様](https://graphql.github.io/graphql-over-http/draft/)は、クライアントがより具体的なタイプ`application/graphql-response+json`をリクエスト（サーバーが応答）することを推奨しています。

この新しいメディアタイプは、ペイロードをGraphQLレスポンスとして識別し、クライアントが他の種類のJSONと区別するのに役立ち、非2xxステータスコードを使用している場合でもレスポンスを安全に処理できるようにします。信頼できるプロキシ、ゲートウェイ、またはその他の仲介者は、JSONを使用してエラーを記述する場合がありますが、有効なGraphQLレスポンスでない限り、`application/graphql-response+json`を使用してエラーを記述することはありません。

### 知っておくべきこと

- サーバーは`application/graphql-response+json`または`application/json`で応答する場合があります。
- クライアントは、`Accept`ヘッダーを使用してこのメディアタイプをリクエストできます：`Accept: application/graphql-response+json, application/json;q=0.9`（古いメディアタイプよりも新しいメディアタイプを優先しますが、両方を受け入れます）
- このコンテンツタイプは推奨されており、そのサポートは拡大しています。
- クライアントがコンテンツネゴシエーションを使用する場合、サーバーが適切なタイプで応答できるか、`application/json`にフォールバックできることを確認してください。
