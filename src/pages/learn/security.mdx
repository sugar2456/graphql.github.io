# セキュリティ

<p className="learn-subtitle">GraphQL APIを悪意のある操作から保護する</p>

あらゆる種類のAPIと同様に、GraphQL実装のサーバーリソースと基盤となるデータソースをリクエスト実行中に保護するために、どのセキュリティ対策を使用すべきかを考慮する必要があります。

多くの一般化可能なAPIセキュリティのベストプラクティスがGraphQLに適用されます。特に、特定の実装が選択したトランスポートプロトコルに関連して。しかし、GraphQL固有のセキュリティ考慮事項もあり、API層を潜在的な攻撃に対してより回復力のあるものにします。

このページでは、GraphQLの潜在的な攻撃ベクトル—その多くはサービス拒否攻撃です—と、多層セキュリティ体制がGraphQL APIを悪意のある操作から保護するのにどのように役立つかを調査します。

## トランスポート層のセキュリティ

GraphQL仕様は、リクエストに特定のトランスポートプロトコルを要求していませんが、ステートレスなクエリとミューテーション操作には[HTTPが一般的な選択肢です](/learn/serving-over-http/)。より長期間にわたるサブスクリプション操作には、WebSocketまたはサーバー送信イベントがよく使用されます。選択されたプロトコルに関係なく、トランスポート層でのセキュリティ考慮事項は、GraphQL APIの重要な第一の防御線を提供できます。

特定のトランスポートプロトコルで提供されるあらゆる種類のAPIに使用されるのと同じセキュリティ対策は、通常、GraphQLにも使用されるべきです。例えば、クエリとミューテーションにHTTPを使用する場合、データを暗号化するためにHTTPSを使用し、リクエストに適切なタイムアウト期間を設定し、HTTPキャッシングを使用する場合、機密データがプライベートにキャッシュされる（またはまったくキャッシュされない）ことを確認する必要があります。

## 需要制御

### 信頼できるドキュメント

ファーストパーティクライアントのみにサービスを提供するGraphQL APIの場合、開発環境で必要に応じて操作を記述し、それらの操作をロックして、本番環境でフロントエンドアプリによってのみ送信できるようにすることができます。具体的には、_trusted documents_を使用することで、スキーマに対して実行できる操作の許可リストを作成できます。

開発中、クライアントはビルドステップとしてGraphQLドキュメントをサーバーの許可リストに送信できます。各ドキュメントは一意のID（通常はそのハッシュ）で保存されます。実行時に、クライアントは完全なGraphQLドキュメントの代わりにドキュメントIDを送信でき、サーバーは既知のドキュメントIDのリクエストのみを実行します。

信頼できるドキュメントは、単に悪意がないと見なされる_persisted documents_です。通常、開発者によって作成され、コードレビューを通じて承認されたためです。[GraphQL-over-HTTP仕様の一部として_persisted documents_を標準化する取り組みが進行中です](https://github.com/graphql/graphql-over-http/pull/264)—ますます多くのGraphQLクライアントとサーバーが既にそれらをサポートしています（時にはレガシーの誤称である_persisted queries_の下で）。

信頼できるドキュメントは、サードパーティクライアントによって送信される操作が事前にわからないため、パブリックAPIには使用できないことに注意してください。ただし、以下の他の推奨事項は、パブリックGraphQL APIを悪意のある操作から保護するのに役立ちます。

### ページネーションされたフィールド

GraphQL APIの需要制御を実装するための最初のステップは、単一のフィールドからクエリできるデータ量を制限することです。フィールドがリスト型を出力し、結果のリストが多くのデータを返す可能性がある場合、単一のリクエストで返される可能性のあるアイテムの最大数を制限するためにページネーションする必要があります。

例えば、この操作で`friends`フィールドの無制限の出力と`friendsConnection`フィールドによって返される制限されたデータを比較してください：

```graphql
# { "graphiql": true }
query {
  hero {
    name
    friends {
      name
    }
    friendsConnection(first: 1) {
      edges {
        node {
          name
        }
      }
    }
  }
}
```

フィールドをページネーションするための接続ベースのモデルについて詳しくは、[ページネーションページ](/learn/pagination/)をご覧ください。

### 深度制限

GraphQLの強みの1つは、クライアントがAPIで公開されているデータ間の関係を反映する表現力豊かな操作を記述できることです。しかし、選択セット内のフィールドが深くネストされている場合、一部のクエリは循環的になる可能性があります：

```graphql
query {
  hero {
    name
    friends {
      name
      friends {
        name
        friends {
          name
          friends {
            name
          }
        }
      }
    }
  }
}
```

基盤となるデータソースへのバッチリクエストを通じてN+1問題が解決された場合でも、過度にネストされたフィールドは、サーバーリソースに過度の負荷をかけ、APIのパフォーマンスに影響を与える可能性があります。

このため、単一の操作が持つことができるフィールドの最大深度を制限することは良いアイデアです。多くのGraphQL実装は、GraphQLドキュメントの最大深度を指定し、リクエストが実行開始前にこの制限を超えた場合にクライアントにエラーを返す設定オプションを公開しています。

リストフィールドのネストは、返されるデータ量の指数関数的な増加をもたらす可能性があるため、リストがネストできる深度に別のより小さな制限を適用することをお勧めします。

クライアントが深くネストされたクエリに対して正当なユースケースを持ち、すべてのクエリに低い包括的な制限を設定することが非現実的な場合、[レート制限](/#rate-limiting)や[クエリの複雑さの分析](#query-complexity-analysis)などの手法に依存する必要がある場合があります。

### 幅とバッチ制限

操作の深度を制限することに加えて、単一の操作に含まれる最上位フィールドとフィールドエイリアスの数を制限するガードレールも配置する必要があります。

次のクエリ操作の実行中に何が起こるかを考えてみましょう：

```graphql
query {
  viewer {
    friends1: friends(limit: 1) { name }
    friends2: friends(limit: 2) { name }
    friends3: friends(limit: 3) { name }
    # ...
    friends100: friends(limit: 100) { name }
  }
}
```

このクエリの全体的な深度が浅いにもかかわらず、APIの基盤となるデータソースは、エイリアスされた`hero`フィールドのデータを解決するために大量のリクエストを処理する必要があります。

同様に、クライアントは、リクエスト内に多くのバッチ操作を含むGraphQLドキュメントを送信する場合があります：

```graphql
query NewHopeHero {
  hero(episode: NEWHOPE) {
    name
  }
}
query EmpireHero {
  hero(episode: EMPIRE) {
    name
  }
}
### ...
query JediHero {
  hero(episode: JEDI) {
    name
  }
}
```

クライアントの実装に応じて、クエリバッチ処理は、ユーザーインターフェースをレンダリングするために必要なすべてのデータを取得するためにサーバーへの往復回数を制限するための有用な戦略である可能性があります。ただし、単一のバッチで許可されるクエリの総数に上限がある必要があります。

深度制限と同様に、GraphQL実装には、操作の幅、フィールドエイリアスの使用、バッチ処理を制限する設定オプションがある場合があります。

### レート制限

深度、幅、バッチ制限は、循環クエリやバッチ攻撃などの広範なカテゴリの悪意のある操作を防ぐのに役立ちますが、特定のフィールドが解決するために計算コストがかかることを宣言する方法を提供しません。そのため、より高度な需要制御要件については、レート制限を実装することをお勧めします。

レート制限は、アプリケーションの異なる層で行われる場合があります。例えば、ネットワーク層またはビジネスロジック層で。GraphQLはクライアントがクエリで必要なデータを正確に指定できるため、サーバーは、リクエストに実行中にリソースに高い負荷をかけるフィールドが含まれているかどうかを事前に知ることができない場合があります。その結果、GraphQL APIに有用なレート制限を適用することは、通常、ネットワーク層で一定期間にわたる受信リクエストの総数を追跡するだけとは異なるアプローチを必要とします。したがって、ビジネスロジック層内でレート制限を適用することが一般的に推奨されます。

### クエリの複雑さの分析

スキーマ内の型とフィールドに重みを適用することで、_query complexity analysis_として知られる手法を使用して、受信リクエストのコストを推定できます。リクエストに含まれるフィールドの組み合わせがリクエストごとの最大許容コストを超える場合、リクエストを完全に拒否することを選択できます。推定コストは、レート制限にも考慮できます：リクエストが進行する場合、リクエストの総コストは、特定の期間にクライアントに割り当てられた全体的なクエリ予算から差し引くことができます。

GraphQL仕様は、APIのクエリの複雑さの分析やレート制限の実装に関するガイドラインを提供していませんが、これらの計算をサポートするカスタム型システムディレクティブを実装するための[コミュニティが維持するドラフト仕様](https://ibm.github.io/graphql-specs/cost-spec.html)があります。

## スキーマの考慮事項

### 引数値の検証とサニタイズ

GraphQLは強く型付けされており、リクエストの[検証段階](/learn/validation/)は、解析されたドキュメントを型システムに対してチェックして、その有効性を判断します。しかし、特定のケースでは、組み込みのスカラー型では、クライアントが提供する引数値がフィールドリゾルバを安全に実行するのに適切であることを確認するのに十分ではない場合があります。

`createReview`ミューテーションで使用される次の`ReviewInput`型を考えてみましょう：

```graphql
input ReviewInput {
  stars: Int!
  commentary: String
}

type Mutation {
  createReview(episode: Episode, review: ReviewInput!): Review
}
```

レビューデータを送信および表示するクライアントアプリケーションの種類に応じて、ユーザーが`commentary`フィールドに安全でないHTMLを送信する場合に備えて、提供された文字列をサニタイズする必要がある場合があります。

サニタイズステップは、`createReview`リゾルバ関数の実行中に呼び出されるビジネスロジック層で行われる必要があります。これをフロントエンド開発者に示すために、カスタム[スカラー型](/learn/schema/#scalar-types)を使用してスキーマの一部として表現することもできます。

### イントロスペクション

[イントロスペクション](/learn/introspection/)は、GraphQL APIのスキーマに関する情報をクエリできるGraphQLの強力な機能です。しかし、ファーストパーティクライアントのみにサービスを提供するGraphQL APIは、非開発環境でイントロスペクションクエリを禁止する場合があります。

イントロスペクションの無効化は「曖昧さによるセキュリティ」の形式として使用できますが、それ自体ではGraphQL APIを完全に曖昧にするには不十分であることに注意してください。これは、潜在的な攻撃者からのAPI情報の発見可能性を制限する、より広範なセキュリティ戦略の一部として使用できます。機密スキーマの詳細とユーザーデータのより包括的な保護については、信頼できるドキュメントと認可を使用する必要があります。

### エラーメッセージ

[レスポンスページ](/learn/response/)で、GraphQL実装が、リクエスト内の検証エラーに関する有用な情報と、これらのエラーに対処する方法に関する提案を開発者に提供する可能性があることを確認しました。例えば：

```graphql
# { "graphiql": true }
query {
  starship(id: 3000) {
    width
  }
}
```

これらのヒントは、クライアント側のエラーをデバッグする際に役立ちますが、本番環境では、公開したい以上のスキーマに関する情報を提供する可能性があります。開発環境以外でGraphQLレスポンス内の詳細なエラー情報を非表示にすることは重要です。なぜなら、イントロスペクションが無効になっている場合でも、攻撃者は間違ったフィールド名で多数の操作を実行することで、最終的にスキーマ全体の形状を推測できる可能性があるためです。

リクエストエラーに加えて、フィールド実行中に発生するエラーに関する詳細は、サーバーまたは基盤となるデータソースに関する機密情報を明らかにする可能性があるため、マスクする必要があります。

## 認証と認可

GraphQL APIの認証関連の考慮事項については、[認可ページ](/learn/authorization/)で詳しく説明しています。

## まとめ

GraphQL APIを保護するためのこれらの推奨事項をまとめると：

- 選択されたトランスポートプロトコルに関する一般的なセキュリティ考慮事項は、通常、GraphQL APIにも適用されます
- 要件に応じて、需要制御は、信頼できるドキュメント、リストフィールドのページネーション、深度制限、幅/バッチ制限、レート制限など、GraphQLで多くの方法で実装できます
- GraphQLスキーマは、クライアントが提供する値の検証とサニタイズをサポートするのに役立ちます
- イントロスペクションの無効化とエラー情報の曖昧化により、APIのスキーマの発見可能性を低くすることができますが、通常、単独で使用するだけでは不十分です（ドキュメント許可リストがより効果的なソリューションである可能性が高いです）
