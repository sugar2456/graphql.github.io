# 認可

<p className="learn-subtitle">認可ロジックをビジネスロジック層に委譲する</p>

ほとんどのAPIでは、リクエストしたユーザーに応じて特定の種類のデータへのアクセスを保護する必要があり、GraphQLも例外ではありません。GraphQLの実行は、[認証](/graphql-js/authentication-and-express-middleware/)ミドルウェアがユーザーの身元を確認し、その情報をGraphQL層に渡した後に開始する必要があります。しかし、その後も、認証されたユーザーがリクエストに含まれる特定のフィールドが提供するデータを閲覧する権限があるかどうかを判断する必要があります。このページでは、GraphQLスキーマが認可をサポートする方法について説明します。

## 型とフィールドの認可

認可は、特定のユーザー/セッション/コンテキストがアクションを実行したり、データを閲覧したりする権限があるかどうかを記述するビジネスロジックの一種です。例えば：

_"作成者のみが自分の下書きを閲覧できる"_

この動作の強制は、[ビジネスロジック層](/learn/thinking-in-graphs/#business-logic-layer)で行う必要があります。スキーマで定義された次の`Post`型を考えてみましょう：
 
```graphql
type Post {
  authorId: ID!
  body: String
}
```

この例では、リクエストが最初にサーバーに到達したとき、認証ミドルウェアがまずユーザーの認証情報を確認し、その身元に関する情報をGraphQLリクエストの`context`オブジェクトに追加して、実行期間中にすべてのフィールドリゾルバでこのデータが利用可能になることを想定できます。

投稿の本文が、その投稿を作成したユーザーにのみ表示されるべきである場合、認証されたユーザーのIDが投稿の`authorId`値と一致するかどうかを確認する必要があります。投稿の`body`フィールドのリゾルバに認可ロジックを配置したくなるかもしれません：

```js
function Post_body(obj, args, context, info) {
  // ユーザーが投稿の作成者である場合のみ、投稿の本文を返す
  if (context.user && context.user.id === obj.authorId) {
    return obj.body;
  }
  return null;
}
```

「作成者が投稿を所有している」ことを、投稿の`authorId`フィールドが現在のユーザーの`id`と等しいかどうかを確認することで定義していることに注意してください。問題点がわかりますか？サービスの各エントリーポイントでこのコードを重複させる必要があります。その後、認可ロジックが完全に同期されていない場合、ユーザーは使用するAPIに応じて異なるデータを閲覧できる可能性があります。これは避けるべきです！GraphQL層に配置するのではなく、認可の[単一の情報源](/learn/thinking-in-graphs/#business-logic-layer)を持つことで、これを回避できます。

リゾルバ内で認可ロジックを定義することは、GraphQLを学習したりプロトタイプを作成したりする際には問題ありません。しかし、本番コードベースでは、認可ロジックをビジネスロジック層に委譲してください。`Post`型のフィールドの認可を別々に実装する方法の例を次に示します：

```js
// 認可ロジックは`postRepository`内に存在する
export const postRepository = {
  getBody({ user, post }) {
    const isAuthor = user?.id === post.authorId;
    return isAuthor ? post.body : null;
  },
};
```

投稿の`body`フィールドのリゾルバ関数は、認可ロジックを直接実装するのではなく、`postRepository`メソッドを呼び出すようになります：

```js
import { postRepository } from "postRepository";

function resolvePostBody(obj, args, context, info) {
  // ユーザーが投稿の作成者である場合のみ、投稿の本文を返す
  return postRepository.getBody({
    user: context.user,
    post: obj,
  });
}
```

上記の例では、ビジネスロジック層が呼び出し元にユーザーオブジェクトを提供することを要求しており、これはGraphQLリクエストの`context`オブジェクトで利用可能です。不透明なトークンやAPIキーではなく、完全にハイドレートされたユーザーオブジェクトをビジネスロジック層に渡すことをお勧めします。このようにすることで、[認証](/graphql-js/authentication-and-express-middleware/)と認可という異なる関心事を、リクエスト処理パイプラインの異なる段階で処理できます。

## 型システムディレクティブの使用

上記の例では、フィールドリゾルバで呼び出される関数を通じて認可ロジックをビジネスロジック層に委譲する方法を見ました。一般的に、すべての認可ロジックをその層で実行することが推奨されますが、代わりにGraphQL層で認可を実装することを決定した場合、1つのアプローチは[型システムディレクティブ](/learn/schema/#directives)を使用することです。

例えば、`@auth`のようなディレクティブをスキーマで定義し、ディレクティブが適用される型とフィールドが提供するデータにアクセスするためにユーザーが持つ必要があるロールや権限を示す引数を持つことができます：

```graphql
directive @auth(rule: Rule) on FIELD_DEFINITION

enum Rule {
  IS_AUTHOR
}

type Post {
  authorId: ID!
  body: String @auth(rule: IS_AUTHOR)
}
```

クライアントが`Post`型の`body`フィールドを含むリクエストを行う場合、`@auth`ディレクティブが実行にどのように影響するかを決定するのは、GraphQL実装次第です。ただし、認可ロジックはビジネスロジック層に委譲されたままである必要があります。

## まとめ

GraphQLでの認可に関するこれらの推奨事項をまとめると：

- 認可ロジックはGraphQL層ではなく、ビジネスロジック層に委譲する必要があります
- 実行が開始された後、GraphQLサーバーは、リクエストを行ったクライアントが含まれるフィールドのデータにアクセスする権限があるかどうかを判断する必要があります
- 一般化された認可ルールを適用するために、型システムディレクティブを定義してスキーマの型とフィールドに追加することができます
